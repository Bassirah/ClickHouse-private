Use this guide to create the ClickHouse accounts that the helper processes of the console sign in with:
`backup_worker`, `access_policy_worker`, `cluster_agent`, and `sso_sync`. The file `service-accounts.sql` of the
`deploy/` directory creates them with the privileges each one needs, and nothing more.

For what each helper does, see [Helper processes](/products/web-console/reference/helper-processes). For the full list
of privileges, see [Service accounts](/products/web-console/reference/privileges#service-accounts).

## Before you begin {#before-you-begin}

- A running server, and an administrator with access management, for example `default` of the deployment.
- The console tables created: select **Set up** on **Component Access**, **Backup & Restore**, **Clusters**, and the
  tabs of **Data Access Policies** that you use (see [Setting up](/products/web-console/guides/component-access#setting-up)).
  The accounts are granted privileges on these tables, in `console_admin` (the `admin_database` setting).
- A password for each account, in `.env` with Docker Compose, or in the Secret on Kubernetes.

## The accounts {#the-accounts}

| Account | Helper | Privileges |
|---|---|---|
| `backup_worker` | Backup worker | A role made with the **Backup Administrator** template, for the databases of the schedules. For server bundles: `CREATE TABLE`, `DROP TABLE`, `INSERT`, `SELECT`, and `BACKUP` on `console_admin.server_bundle*`. |
| `access_policy_worker` | Access policy worker | `SELECT` on `console_admin.*`; `INSERT` on `dap_owned`, `dap_deployments`, `audit_log`, and, with an attribute feed, `dap_user_attributes`; `SELECT` on `system.users`, `roles`, `role_grants`, `grants`, and `row_policies`; `SHOW USERS`, `SHOW ROLES`, `SHOW ROW POLICIES`; `IMPERSONATE` on each rule author. |
| `cluster_agent` | Cluster agent | `SELECT` and `INSERT` on `clusters`, `cluster_revisions`, `cluster_operations`, `cluster_events`, `cluster_observations`, and `cluster_resources`; `SELECT` on `cluster_capabilities` and `backup_destinations`; `INSERT` on `audit_log`; `IMPERSONATE` on each user who requests cluster operations. |
| `sso_sync` | Token authenticator, for its user sync | `CREATE USER`, `ALTER USER`, `DROP USER`; `SHOW USERS`, `SHOW ROLES`; `SELECT` on `system.users`, `roles`, and `role_grants`; `INSERT` on `audit_log`; the roles of the groups `WITH ADMIN OPTION`. |

Each account is created `IDENTIFIED WITH sha256_password`, with its password passed as a query parameter, so that the
password is not written in the file.

## Fill in the placeholders {#fill-in-the-placeholders}

The privileges that depend on your deployment are placeholders in angle brackets. The lines that contain one are
commented out, so that nothing is granted by guess. Edit `service-accounts.sql`, and replace each with real names:

1. **The role of the backup worker.** Create a role with the **Backup Administrator** template on **Roles &
   Permissions** (see [Role templates](/products/web-console/guides/users-and-roles#role-templates)), for the databases
   that the schedules back up. The template lists its exact privileges before it creates the role. Then:

   ```sql
   GRANT backup_admin TO backup_worker;
   ```

2. **The rule authors of the access policy worker.** The worker acts as the author of each rule, with
   `EXECUTE AS`, so it needs no privilege to grant anything itself, only the right to impersonate the authors:

   ```sql
   GRANT IMPERSONATE ON alice TO access_policy_worker;
   ```

3. **The requesters of the cluster agent.** The agent checks the capabilities of each requester with
   `EXECUTE AS <user> CHECK GRANT`:

   ```sql
   GRANT IMPERSONATE ON alice TO cluster_agent;
   ```

4. **The roles of the user sync.** Grant the roles that the groups `clickhouse-<role>` stand for, and the default roles
   of the sync, with the admin option, so that the sync can grant those and no other role:

   ```sql
   GRANT analysts, console_admin_reader TO sso_sync WITH ADMIN OPTION;
   ```

   `ROLE ADMIN` would also work, but lets the account grant every role.

The section of `sso_sync` is commented out in the file: uncomment it only with single sign-on. Delete the sections of
the other accounts you do not deploy, for example `cluster_agent` without the cluster agent, and leave out their
parameters below. The names `backup_admin` and `alice` are examples.

## Run the file {#run-the-file}

Run the file as the administrator, with one `--param_` argument per account: `backup_pw`, `policy_pw`, `agent_pw`,
and, with single sign-on, `sso_pw`. A parameter that a statement uses but the command does not pass stops the file at
that statement.

<Tabs>
<Tab title="Docker Compose">

In the `deploy/` directory, with the passwords of `.env`:

```bash
set -a; . ./.env; set +a
docker compose exec -T clickhouse clickhouse-client --password "$CLICKHOUSE_ADMIN_PASSWORD" \
    --param_backup_pw="$BACKUP_WORKER_PASSWORD" --param_policy_pw="$ACCESS_POLICY_WORKER_PASSWORD" \
    --param_agent_pw="$CLUSTER_AGENT_PASSWORD" \
    --multiquery < service-accounts.sql
```

With the section of `sso_sync` uncommented, add `--param_sso_pw="$SSO_SYNC_PASSWORD"`.

</Tab>
<Tab title="Kubernetes">

With the passwords of the Secret `clickhouse-console-passwords`:

```bash
secret() { kubectl -n clickhouse-console get secret clickhouse-console-passwords -o "jsonpath={.data.$1}" | base64 -d; }
kubectl -n clickhouse-console exec -i clickhouse-0 -- clickhouse-client --password "$(secret admin)" \
    --param_backup_pw="$(secret backup_worker)" --param_policy_pw="$(secret access_policy_worker)" \
    --param_agent_pw="$(secret cluster_agent)" \
    --multiquery < service-accounts.sql
```

The Secret of `kubernetes.yaml` has no password for `sso_sync`: to use single sign-on, add a key for it, uncomment the
section of `sso_sync`, and add its `--param_sso_pw`.

</Tab>
</Tabs>

The statements use `CREATE USER IF NOT EXISTS`, and the grants can be repeated, so you can run the file again after
changing it. An existing account keeps its password: to change one, use `ALTER USER ... IDENTIFIED WITH sha256_password
BY ...`, then update the password of the helper and restart it.

## Verify {#verify}

```sql
SHOW GRANTS FOR backup_worker;
SHOW GRANTS FOR access_policy_worker;
SHOW GRANTS FOR cluster_agent;
SHOW GRANTS FOR sso_sync;
```

Then start the helpers. Their heartbeats appear on **Backup & Restore → Overview** and on the Cluster Inventory, and the
token authenticator logs `users synced`.

## Least privilege {#least-privilege}

- **One account per helper.** Do not share an account between helpers, and do not run a helper as `default`.
- **Impersonation, not grants.** The access policy worker and the cluster agent act as the users they work for, with
  `EXECUTE AS`, so ClickHouse checks those users' privileges. Grant `IMPERSONATE` only on the users who author rules or
  request cluster operations.
- **Named roles for the sync.** Grant `sso_sync` the roles of the groups `WITH ADMIN OPTION` rather than `ROLE ADMIN`.
  The sync changes only the users identified with its authentication server; checking tokens needs no account at all.
- **The backup role.** Limit the role of the backup worker to the databases of the schedules. Grant the server bundle
  tables only when you use server bundles.
- **Protect the accounts.** Mark the service accounts as protected accounts, so that the console does not delete or
  suspend them (see [Protected accounts](/products/web-console/guides/users-and-roles#protected-accounts)), and keep
  `.env` readable by its owner only (`chmod 600`).
