The web console is a single entry point for the web UIs built into the ClickHouse server. It is served from any ClickHouse HTTP port at the `/console` path, for example `http://localhost:8123/console`.

Open the console, sign in with a ClickHouse user, and pick a panel on the home page. Panels open in the main area next to a sidebar that stays visible, so you can switch between the SQL Console, dashboards, and diagnostics without signing in to each of them.

## Panels {#panels}

The home page and the sidebar list the same destinations:

| Category | Destination | Path | How it receives the connection |
|---|---|---|---|
| Home | Home | `/console/home` | — |
| Workspace | SQL Console | `/ui` | The console fills in the connection form of the SQL Console. |
| Workspace | Dashboard | `/dashboard` | Console integration contract. |
| Workspace | ClickStack | `/clickstack` or `clickstack_url` | ClickStack keeps its own connection settings. |
| Workspace | Web Terminal | `/webterminal` | The `webterminal-credentials` message. |
| Diagnostics | Binary visualizer | `/binary` | Console integration contract. |
| Diagnostics | Merges visualizer | `/merges` | Console integration contract. |
| Diagnostics | Schema visualizer | `/schema` | Console integration contract. |
| Diagnostics | Jemalloc | `/jemalloc` | Console integration contract. |
| Diagnostics | Processors profile | `/processors-profile` | Console integration contract. |
| Administration | Users, Roles & Permissions, Component Access, Profiles & Quotas, Audit Activity | `/console/admin-*` | Pages of the console itself (see [Administration](#administration)). |
| Resources | Source code, Documentation, Website, Cloud | `source_code_url`, `documentation_url`, `website_url`, `cloud_url` | None: opened in a new tab. |
| Resources | Reference | `/docs` | Console integration contract. |

When a panel opens, the console header and sidebar hide, so that the panel, with its own navigation, uses the whole window. To return to the console navigation, select **Console** (the arrow at the start of the panel bar); select the same button again to hide it. The console navigation stays visible for that panel until you select another one. Home, the [Administration](#administration) pages, and the messages shown instead of a panel (for example when it is restricted or not configured) always show the console navigation. In the Web Terminal, Escape moves the keyboard focus to the **Console** button.

Each panel has a refreshable address under `/console`, for example `/console/merges`. The browser's Back and Forward buttons move between panels. The pages keep working on their own at their original paths.

After sign-in, the console runs a `LIMIT 0` query for each diagnostic panel with the privileges that panel needs. A panel is:

- Not listed when the server denies that query: the user has no privileges for the panel, so the console shows neither its card nor its sidebar entry. Its address, for example `/console/merges`, explains the restriction and can still open the panel; the server rejects every query the user is not allowed to run.
- **Unavailable** when a system table the panel needs does not exist, for example when `system.part_log` is not configured.
- **Not configured** when an administrator has removed its address (see [Configuration](#configuration)).
- **Needs Internet** when the page loads a library from a public CDN: the Binary visualizer loads Leaflet, and Jemalloc loads uPlot. Every other panel and the console itself work without Internet access.

The Web Terminal is unavailable when it is disabled with the `enable_webterminal` server setting, and when the console is connected to a server other than the one that serves it.

## Signing in and out {#signing-in-and-out}

The sign-in form asks for a username and a password. The console signs in to the server that serves it, at the address of the page. It checks the credentials by running `SELECT currentUser(), version(), hostName()`, which needs no privileges. If the check fails, it tells apart:

- an incorrect username or password;
- a user that may not connect from your address, or that lacks permissions;
- a server that cannot be reached.

If you open a panel's address without being signed in, the console asks you to sign in and then opens that panel.

**Sign out** and **Switch connection** (to sign in as another user) close every panel, which ends their queries, timers, and terminal sessions. They also discard the password and the ClickHouse connection that ClickStack stored for the current browser tab. After signing out, the Back button does not restore the signed-in state.

The home page shows the connection status the server reported at the last check. The console checks the connection again every minute while the tab is visible, and when you select **Check connection**.

## Security model {#security-model}

The sign-in screen is a convenience of the user interface, not an access control: the console page and the embedded pages are public static files, like the other web UIs. Every query is authorized by the ClickHouse server, with the credentials of the signed-in user. Hiding or marking a panel in the console does not change what the user can do.

Credentials are handled as follows:

- The console keeps the password in the memory of the browser tab. It is never written to the address bar, the browser history, cookies, or browser storage. Reloading the page signs you out.
- The console sends the credentials in the `X-ClickHouse-User` and `X-ClickHouse-Key` headers.
- Embedded pages get the credentials from the console without going through a URL, a storage, or a message to another origin (see [Integration contract](#integration-contract)). Some of them send the credentials to the server as `user` and `password` URL parameters, as they do when opened on their own. The ClickHouse server masks the password in its logs, but a reverse proxy may record such URLs: do not log query strings on a proxy in front of ClickHouse.
- Links to external destinations open in a new tab with `noopener` and `noreferrer`, and carry no credentials, queries, or database names.
- The console page is served with `Cache-Control: no-store`, `X-Frame-Options: DENY`, and a `Content-Security-Policy` that allows only inline code, same-origin frames, and requests to ClickHouse servers. To override any of these headers, set it in the [`http_handlers`](/interfaces/http#predefined_http_interface) configuration of a `console` handler.
- The embedded pages are loaded in same-origin frames. Do not set `X-Frame-Options: DENY` or `frame-ancestors 'none'` on them, or they cannot be embedded.

The SQL Console keeps its saved queries, query history, and open tabs in the browser's local storage, per server URL and user, also when it is used inside the console. Signing out of the console does not delete them.

## Configuration {#configuration}

The destinations of the resource links and of ClickStack are set in the `web_console` section of the server configuration. A path on the server is opened inside the console; an absolute HTTP or HTTPS URL is opened in a new tab; an empty value marks the destination as not configured. Other values are rejected.

| Setting | Default |
|---|---|
| `source_code_url` | `https://github.com/ClickHouse/ClickHouse/` |
| `documentation_url` | `https://clickhouse.com/docs/` |
| `website_url` | `https://clickhouse.com/` |
| `cloud_url` | `https://clickhouse.cloud/` |
| `clickstack_url` | `/clickstack/` |
| `admin_database` | `console_admin`: the database of the [administration tables](#console-tables) |
| `backup_s3_endpoints` | Empty: the S3 endpoints that [backup destinations](#backup-destinations) may use, separated by commas: exact endpoints such as `https://minio.example.com:9000`, or [patterns](#s3-endpoint-allowlist) such as `https://*.amazonaws.com`. With an empty value, only disk destinations can be added. |

For example, in a network without Internet access, point the documentation to an internal mirror and remove the other external links:

```xml
<clickhouse>
    <web_console>
        <documentation_url>https://docs.example.internal/clickhouse/</documentation_url>
        <source_code_url></source_code_url>
        <website_url></website_url>
        <cloud_url></cloud_url>
    </web_console>
</clickhouse>
```

The console reads these settings from `/console/config.json`, so a configuration reload applies them without restarting the server.

To serve the console with custom response headers, use the `console` handler type in `http_handlers`. The console works only at `/console`, so the rule must match every path under it, including `/console/config.json`:

```xml
<clickhouse>
    <http_handlers>
        <rule>
            <url>regex:^/console(/.*)?$</url>
            <methods>GET,HEAD</methods>
            <handler>
                <type>console</type>
            </handler>
        </rule>
        <defaults/>
    </http_handlers>
</clickhouse>
```

## Administration {#administration}

The **Administration** category manages ClickHouse users, roles, settings profiles, and quotas, and the access policy of the console. Its pages are listed for users who can read what they show; for everyone else they are hidden. Hiding is a convenience only.

| Page | What it does |
|---|---|
| Users | Searchable, paginated list of users with their authentication methods, management source, roles, allowed hosts, profiles, quotas, and state. Each user has tabs for its overview, roles, permissions, profiles and quotas, component access, and audit activity. |
| Roles & Permissions | Roles with their privileges, members, and granted roles; grants and revokes of privileges on everything, a database, a table, or columns; role templates. |
| Component Access | Which console components each role or user can open, compared with the native privileges that actually govern them; protected accounts. |
| Profiles & Quotas | Settings profiles with limits and constraints, and quotas with their intervals and limits. |
| Audit Activity | Changes made in the console, and access-management statements that the server logged, including those made outside of the console. |

### Identity and authorization model {#identity-and-authorization-model}

The console has no identity provider and no server-side session: you sign in as a ClickHouse user, and the password stays in the memory of the browser tab. Every administrative action is a statement such as `CREATE USER` or `GRANT`, built by the console from validated form fields (it never runs SQL typed by the user), and run with your credentials. ClickHouse authorizes each statement:

- granting a privilege needs that privilege `WITH GRANT OPTION`, so you cannot hand out more than you have;
- granting a role needs `ROLE ADMIN`, or that role granted to you `WITH ADMIN OPTION`;
- user management can be limited to names: `GRANT CREATE USER, ALTER USER, DROP USER ON app_* TO ...` allows managing only the users whose names start with `app_`.

The console asks the server what you can do (`CHECK GRANT`, and `LIMIT 0` reads of system tables) to decide which pages and buttons to offer. The server still checks every statement, so a direct request without the console is rejected in the same way.

A ClickHouse user is a database identity. Creating one does not create an account in ClickStack or in any other separately deployed service, and the console does not synchronize identities with them.

Users defined in configuration files (`users.xml`) and users provided by an LDAP server are shown with their source and are read-only in the console: SQL statements cannot change them, and the console does not move users between sources. ClickHouse does not store e-mail addresses, creation dates, or the time of the last login, so the console does not show them; the last successful login is shown from `system.session_log` when that log is enabled.

### Setting up {#setting-up}

The Users, Roles & Permissions, and Profiles & Quotas pages work without setup. The audit log, the component access policy, and the protected accounts need tables: on the **Component Access** page, select **Set up**. This creates the database named by the `admin_database` setting (by default `console_admin`) with the [console tables](#console-tables), and a policy rule that lets all users open every component, so nothing changes for users until you edit the policy. The setup needs `CREATE DATABASE` (if the database does not exist) and `CREATE TABLE` on it.

Users who cannot read the policy table do not see the components it governs. The setup therefore creates the role `<admin_database>_reader` (by default `console_admin_reader`) with `SELECT` on the policy table, and offers to assign it to the existing users and roles created with SQL. The role must be among a user's default roles to apply at sign-in. When you create a user in the console, this role is preselected if you can grant it. A role is used instead of a direct grant because assigning a role needs only the admin option on it, while granting `SELECT` on the table would need it `WITH GRANT OPTION`.

To set up without the console, run the statements shown in the review step of the **Set up** dialog with `clickhouse-client`.

### User lifecycle {#user-lifecycle}

- **Create**: a name, a password (typed twice, or generated in the browser and shown once after the user is created), an optional expiry, the allowed hosts, a default database, roles, and a settings profile.
- **Edit**: rename, allowed hosts, and default database.
- **Password**: set a new password or generate a temporary one, with an optional expiry. This replaces every authentication method of the user. ClickHouse cannot force a password change at the next login; use an expiry instead. Users authenticated by LDAP, Kerberos, certificates, SSH keys, JWT, or HTTP cannot get a password in the console.
- **Roles**: assign and revoke roles, set the default roles, and grant the admin option.
- **Delete**: shows what depends on the user (roles, privileges, views with `SQL SECURITY DEFINER` that run as the user, quotas, row policies, and running queries) and asks you to type the name.

Passwords are sent to the server only in the statement that sets them, never in a URL. The server stores a hash and masks the password in `system.query_log` and its logs. The console does not write passwords to the audit log, to error messages, or to browser storage, and removes a generated password from the page when its dialog closes.

### Suspending a user {#suspending-a-user}

ClickHouse has no statement that disables a user. The console suspends a user with `ALTER USER name VALID UNTIL '2000-01-01 00:00:00 UTC'`, which makes every authentication method of the user expire. Then:

- new logins are rejected over every interface. HTTP requests are authenticated one by one, including those with a `session_id`, so HTTP clients of the user stop working at their next request;
- native connections that are already open, such as `clickhouse-client`, the Web Terminal, and pooled driver connections, keep working until they disconnect. ClickHouse has no statement that closes another user's connection. To cut them off at once, revoke the user's roles and privileges as well: revocations apply to open sessions at their next query;
- running queries finish, unless you also select **Stop running queries**, which runs `KILL QUERY` and needs the `KILL QUERY` privilege;
- roles, privileges, and settings stay unchanged.

**Reactivate** sets `VALID UNTIL 'infinity'` or a date you choose. Expiry dates that the user had before the suspension are overwritten; they are kept in the audit record and shown when reactivating.

### Roles and templates {#roles-and-templates}

The permissions of a user or role are shown as direct privileges, privileges inherited from roles (with the role path, and whether the role is a default role, which is active at login, or needs `SET ROLE`), and the effective privileges computed by the server (`SHOW GRANTS ... FINAL`). Grants with the grant option and roles with the admin option are marked, because they allow delegation.

The role templates are proposals of the console, not built-in ClickHouse roles. None includes the grant option or unrestricted administrative rights. The console shows each template's exact privileges before creating a role, and the server refuses any privilege you do not hold `WITH GRANT OPTION`.

| Template | Privileges |
|---|---|
| Platform Administrator | `SELECT, INSERT` on the three console tables; `SHOW USERS, SHOW ROLES ON *.*`. |
| ClickHouse Access Administrator | `CREATE USER, ALTER USER, DROP USER ON <pattern>`; `SHOW USERS, SHOW ROLES, SHOW SETTINGS PROFILES, SHOW QUOTAS ON *.*`; `SELECT, INSERT` on the audit log and `SELECT` on the policy and the protected accounts; the chosen roles and, once the console is set up, `<admin_database>_reader` `WITH ADMIN OPTION`; optionally `KILL QUERY ON *.*`. |
| Database Administrator | On each chosen database: `SHOW, SELECT, INSERT, ALTER, CREATE TABLE, CREATE VIEW, CREATE DICTIONARY, DROP TABLE, DROP VIEW, DROP DICTIONARY, TRUNCATE, OPTIMIZE`, and `SYSTEM MERGES, SYSTEM TTL MERGES, SYSTEM MOVES, SYSTEM FETCHES, SYSTEM REPLICATION QUEUES, SYSTEM SYNC REPLICA, SYSTEM RESTART REPLICA`. |
| Developer | On each chosen database: `SHOW, SELECT, INSERT, ALTER TABLE, ALTER VIEW, CREATE TABLE, CREATE VIEW, DROP TABLE, DROP VIEW, TRUNCATE, OPTIMIZE`; `CREATE TEMPORARY TABLE ON *.*`. |
| Analyst | `SHOW TABLES, SHOW COLUMNS, SELECT` on each chosen database. |
| Operator | `SELECT` on `system.dashboards`, `metric_log`, `asynchronous_metric_log`, `metrics`, `events`, `asynchronous_metrics`, `part_log`, `merges`, `mutations`, `replicas`, `parts`, `disks`, `clusters`, `tables`, `columns`, `dictionaries`, `jemalloc_stats`, `documentation`; optionally `system.processes`, `query_log`, and `processors_profile_log` (they contain the queries of all users) and `INTROSPECTION`. |
| Auditor | `SHOW USERS, SHOW ROLES, SHOW SETTINGS PROFILES, SHOW QUOTAS, SHOW ROW POLICIES ON *.*`; `SELECT` on the three console tables, `system.query_log`, and `system.session_log`. |

The access administrator pattern `*` lets the role change any user, including administrators: prefer a prefix.

### Component access {#component-access}

The policy has rules for all users, for roles, and for users. Each rule allows four capabilities of a component: **Open**, **View data**, **Run queries**, and **Administer**. A capability is allowed when any rule for all users, for the signed-in user, or for one of the roles enabled in the session allows it; components without a rule that allows **Open** are not listed, and their address shows that the policy does not allow them. The policy governs the panels, the links of the **Resources** section (Source code, Documentation, Website, Cloud, and Reference), and the administration pages (Users, Roles & Permissions, Profiles & Quotas, Audit Activity, Backup & Restore, and Clusters). For a link and an administration page, only **Open** applies: what a user can do on an administration page is decided by native privileges, as before, and a page is listed only when the user can also read what it shows. To give an administration page to some roles only, untick **Open** for all users and tick it for those roles. Home and Component Access itself are not governed: Component Access stays available to the users who can change the policy, so a policy mistake cannot lock them out of correcting it. A component that no rule mentions yet, such as one added to the console after the policy was set up, is open to everyone; on the Component Access page it is marked **No rules yet**, and saving the rules for all users turns that into a rule. Hiding a link only removes it from the console: anyone who knows the address of an external site can still visit it.

The console enforces only **Open**. The SQL Console, the standalone pages, the Web Terminal, and other clients reach the server directly, where only native privileges apply. For the other capabilities, the Component Access page shows the native privileges that govern them (for example `SELECT ON system.part_log` for the Merges visualizer), whether a role or user has them, and offers to grant the missing ones or revoke direct grants where the policy and the grants disagree. ClickStack has its own connection settings and authorization, and the Web Terminal is enabled for everyone by the `enable_webterminal` server setting: the policy only hides them in the console.

When the policy table exists but the user cannot read it, the console does not list the governed components and says so on the home page.

### Protected accounts and platform administrators {#protected-accounts}

Protected accounts are users that the console does not delete or suspend, for example break-glass accounts. Users defined in configuration files cannot be changed with SQL at all, which makes them the most robust break-glass accounts.

Platform administrators are the users who can change the policy (`INSERT` on its table, directly, through roles, or through broader grants). The console estimates them from `system.grants` and refuses to delete or suspend the last one, to revoke the last role that makes someone one, or to delete such a role.

These safeguards are applied by the console only. A user with the privileges can still make the same changes with SQL directly.

### Clusters {#clusters}

Changes apply to the server the console is connected to. When the server has clusters and its SQL-managed users are not in a replicated user directory, the administration pages offer **Apply changes to: ON CLUSTER**. Each statement then runs with `ON CLUSTER` and `distributed_ddl_output_mode = 'never_throw'`, and the result shows every server with its outcome. A server that does not answer within 30 seconds is shown as unfinished: it executes the statement when it processes the distributed DDL queue. A change that fails on some servers is reported as partially applied; it is not rolled back. When users are stored in a `replicated` user directory, every change reaches all servers that share it through Keeper, and the console does not offer `ON CLUSTER`.

Statements of one change run one after another and stop at the first failure, because ClickHouse has no transactions for access entities. The result lists the steps that took effect.

The console tables are stored on the server the console is connected to, and are not replicated.

### Audit activity {#audit-activity}

The **Console actions** tab shows the records that the console writes after each change: the actor, the time, the server, the scope (this server or a cluster), the target, the action, a summary, the result (`success`, `failure`, or `partial`), a sanitized error, and the steps with the outcome on each server. Each change has a correlation ID, which the console also sets as the `log_comment` of its statements.

The **Access changes seen by the server** tab shows `CREATE`, `ALTER`, and `DROP` statements for users, roles, profiles, quotas, and policies, and `GRANT` and `REVOKE`, from `system.query_log`, including rejected attempts. Statements with a console correlation ID are marked as made in the console, all others as made outside of it. This covers only the server the console is connected to, and does not cover users or sessions with `log_queries` disabled, changes to configuration files, or statements older than the `query_log` retention.

The **Access decisions** tab shows query-time authorization decisions, apart from administrative changes: reads the server refused with `ACCESS_DENIED`, from `system.query_log`, with the literals of the queries replaced by `?`, and the runs of access tests (see [Data Access Policies](#data-access-policies)). Statements of the access policy worker run as `EXECUTE AS <rule author>` and appear on the server tab.

The pages always read the current state from the server, so a change made outside of the console is shown on the next load or refresh.

### Console tables {#console-tables}

| Table | Contents |
|---|---|
| `audit_log` | `MergeTree` with the console's audit records. Records older than the retention chosen at setup (365 days by default) are removed by a TTL. |
| `component_policy` | `ReplacingMergeTree` with one row per subject and component, read with `FINAL`. |
| `protected_accounts` | `ReplacingMergeTree` with the protected users. |

The actor, the time, and the server of each row are columns that the server fills in (`MATERIALIZED currentUser()`, `now64()`, and `hostName()`), with `CHECK` constraints that reject other values even when `insert_allow_materialized_columns` is enabled. So a user who can insert into these tables cannot write rows in another user's name. They are ordinary tables, though: users with `ALTER`, `TRUNCATE`, or `DROP` on them can change or remove rows, so the audit log is not tamper-proof. Grant only `SELECT` and `INSERT` on them, and keep `ALTER` and `DROP` to the server administrators. To change the retention later, run `ALTER TABLE console_admin.audit_log MODIFY TTL toDateTime(event_time) + INTERVAL <days> DAY`.

To remove the administration data, drop the database. The console then works as if it was never set up.

## Data Access Policies {#data-access-policies}

The **Data Access Policies** page of the **Administration** category controls which columns and rows of tables each user can read, explains the effective access of a user, and provisions native controls from trusted user attributes. Hiding a component in the console is not data authorization: only the server controls on this page are, and they apply to every client that reaches the server, including the SQL Console, BI tools, drivers, the HTTP interface, and the native protocol.

The page keeps five mechanisms apart:

| Mechanism | What it is | Enforced by | On this page |
|---|---|---|---|
| Column permissions | Native `GRANT SELECT(column) ON db.table` | The server, for every query | **Column Permissions**, **Effective Access** |
| Row policies | Native `CREATE ROW POLICY ... USING <filter>` | The server, for every `SELECT` | **Row Policies**, **Effective Access** |
| Attribute-driven provisioning | Rules on user attributes, translated into native roles, grants, and row policies | The server, after a deployment or reconciliation | **Attributes & Classifications**, **Policy Rules**, **Policy Deployments** |
| Dynamic, request-time ABAC | A decision per query from attributes of the request (purpose, device, time, network) | Not provided | Rules on such attributes are refused |
| Column masking | Returning a transformed value instead of the stored one | Not provided: native masking policies are refused by this build | Not offered |

Attribute-driven provisioning is not per-query ABAC: a change of an attribute takes effect when the rules are deployed or reconciled, not on the next query. The console does not present views as masking policies.

### Verified behavior {#data-access-verified-behavior}

These are the behaviors of the server version this page was built for, checked on it with synthetic users and data. Confirm them on another release with the access tests.

| Requirement | Existing capability | Enforcement point | Added by the console | Version limitation |
|---|---|---|---|---|
| Read only some columns | `GRANT SELECT(col, ...)` | Query analysis on the server that runs the query | Column matrix, grant and revoke with review, broader-grant detection | `SELECT *` fails unless every column is granted; `count()` works with any column grant |
| Read only some rows | `CREATE ROW POLICY ... AS permissive / restrictive` on a table or `db.*` | Every `SELECT` on the server that reads the table | Structured filter editor, combined filter per user, bypass paths | Filters reads only; not `INSERT`, `ALTER UPDATE`, or `ALTER DELETE` |
| Users without a matching policy | `access_control_improvements.users_without_row_policies_can_read_rows` (default `true`) | Server configuration | Flagged per user as "All rows: no policy applies" | The setting cannot be read with SQL: the console assumes the default |
| Explain effective access | `system.grants`, `system.role_grants`, `system.row_policies`, `SHOW GRANTS ... FINAL` | — | Role paths, default and activatable roles, conflicts, sources | Shows one server; sessions of other users are not observable |
| Verify access at runtime | `EXECUTE AS <user>` with `IMPERSONATE ON <user>` | The server, with the target user's grants, default roles, and row policies | **Verify with the server**, access tests | Needs `allow_impersonate_user` and `IMPERSONATE` per target user |
| Distributed reads | Shards apply their own row policies for the connecting user and those of the initial user, if a user of that name exists on the shard | Each shard | Distributed tables listed as bypass paths | Column grants are checked on the Distributed table, not on the shard's table |
| Reads through views | `SQL SECURITY DEFINER` and `NONE` views read as their definer | The view | Listed as bypass paths | Row policies of the reader on the base table do not apply inside the view; `currentUser()` inside still returns the reader |
| Masking | `CREATE MASKING POLICY` | — | Not offered | Refused: "Masking Policies are available only in ClickHouse Cloud" |

### Column permissions {#data-access-column-permissions}

**Column Permissions** shows, for a chosen table, a matrix of users and roles against columns: ✓ for a column grant, ● for a grant on the whole table, the database, or every database, and parentheses when the grant comes from a role that is not a default role (active only after `SET ROLE`). Below it are the broader grants, with the role path that gives them and whether they override column grants; the direct column grants to users; and grants on columns that no longer exist.

Column grants are positive: a narrow grant never cancels a grant on the whole table or a wider one, which still gives every column. To restrict a user to some columns, revoke the broader grant (or add a partial revoke), then grant the columns, preferably to a role. A column grant covers the existing columns only; table, database, and global grants also cover columns and tables created later. A renamed column keeps its grant under the old name, which then names a column that no longer exists: the page lists such grants with **Revoke**.

**Grant columns** grants `SELECT` on the chosen columns to a role or a user. The review warns when the grantee already reads every column through a broader grant, so that the change has no effect, and when `SELECT *` will fail for it.

### Row policies {#data-access-row-policies}

**Row Policies** lists every row policy with its table or database, kind, filter, targets, and source, and offers **Create row policy**, **Edit**, and **Remove**. The editor writes the filter from conditions on columns of the table (`=`, `≠`, "is one of", "is none of", and "= the user name" for `currentUser()`), joined with `AND`, with values quoted for the column's type, and offers presets for columns such as `branch`, `company`, `tenant`, and `region`. An expression can be typed only by administrators who can create and alter row policies on every table (`CREATE ROW POLICY, ALTER ROW POLICY ON *.*`); it is checked with the server's parser (`EXPLAIN AST`, `EXPLAIN QUERY TREE`) and refused when it contains subqueries, table functions, or references to other tables. The review lists the affected users with their combined filter before and after the change.

**Effect on a table** shows, for each user who can read the table or to whom a policy applies, the rows visible at login: all rows (no policy exists, or none applies to the user), no rows, or the combined filter, which is the permissive policies joined with `OR`, and the restrictive ones with `AND`. It also lists:

- **Bypass paths**: views that run as their definer, materialized views, and Distributed, Merge, and Buffer tables whose definition names the table. A match by name is a candidate for review, not a proof.
- **Users who can change rows**: users with `INSERT`, `ALTER UPDATE`, `ALTER DELETE`, or wider grants, who can write rows outside their filter.

On a cluster, row policies are evaluated by the server that reads the table. Create them `ON CLUSTER` (or in a replicated user directory) so that every shard has them, and configure an interserver `<secret>` for the cluster so that the shards know the initial user.

### Effective access {#data-access-effective-access}

**Effective Access** explains, for a user, a table, and an operation (`SELECT` or `INSERT`):

- the identity, its source (SQL, configuration, LDAP), state, and default roles;
- the roles granted to the user with their paths, which are active at login, and which apply only after `SET ROLE`;
- per column, whether the configured grants give it at login and with all granted roles, and which grant gives it, directly or through which role path;
- the row filter at login and with all granted roles, and the policies with their sources;
- conflicts: column grants made ineffective by a broader grant, several permissive policies, a filter that changes with `SET ROLE`, and policy rules whose intent other grants contradict.

Inspecting grants is not a proof. The page distinguishes the configured entitlement, the access in the default-role context, the result verified by the server, and what is unknown. **Verify with the server** runs `EXECUTE AS <user> CHECK GRANT` for every column and counts the visible rows as the user. It needs `IMPERSONATE` on that user: grant it only on dedicated test users. Without it the result is shown as unknown, with the server's message.

### Access tests {#data-access-tests}

**Access Tests** stores approved positive and negative tests: a user, a table, columns (or only a count of the rows), and the expected outcome: allowed, optionally with a number of rows, or denied (`ACCESS_DENIED`). **Run** reads the table as the user with `EXECUTE AS`, so the server applies that user's grants, default roles, and row policies as for a direct connection. An error other than `ACCESS_DENIED`, including a missing `IMPERSONATE` grant, is an error, never a pass. A run records the outcome and the number of rows, never the data.

The browser acceptance checks (`utils/web-console/data_access_e2e.mjs`) repeat the checks over HTTP and with the native client, as the synthetic users themselves.

### Attributes and classifications {#data-access-attributes}

An attribute definition names the attribute, its category (user, resource, operation, or environment), whether it is evaluated per request, its source of truth, its **writer**, its owner, and how long a value stays fresh. The writer is the database user whose values are trusted, typically the account of an identity provider or HR import. The server records who wrote each value (`MATERIALIZED currentUser()`); a value written by anyone else, a value older than the freshness limit, or a value of an undefined attribute is shown as **Not trusted** and treated as missing. ClickHouse does not read identity provider claims itself: values reach it only through this table, and nothing a browser sends is taken as evidence.

The reserved user attribute `employment_status` disables an identity for every rule when its value is `disabled`, `suspended`, `terminated`, or `inactive`.

Data classifications label columns (for example `pii`, `financial`, or `secret`) with their source and owner. A label does not hide a column by itself: rules give access to the columns of a label.

### Policy rules {#data-access-rules}

A rule selects users with conditions on user attributes (all must hold) and provisions one of:

| Kind | Example | Generated native controls |
|---|---|---|
| Grant a role | Analysts in department Finance get the role `finance_reports` | `GRANT finance_reports TO <user>` per matched user |
| Filter rows by an attribute | Branch staff read only the rows of their branch | One permissive row policy per value, `dap_<rule>_<value hash>`, `USING branch = '<value>' TO <users>`; and `dap_<rule>_none`, `USING 0`, for users in scope without a trusted value and for disabled identities |
| Columns of a label need a clearance | Users without clearance `secret` cannot read columns labeled `secret` | A role `dap_<rule>_cleared` with `SELECT(<column>)` on every column of the label, granted to the cleared users |

Each rule also says what happens when an attribute is missing or stale: **revoke** (default: what the rule gave is removed, and a row filter shows no row) or **keep** (what was provisioned from the last known value stays until the value is fresh again; nothing new is provisioned from a stale value). **Exceptions** lists users the rule never provisions, for an entitlement revoked on purpose.

Rules only add access. A rule never removes a grant made outside the platform, so this is not deny-overrides: a user who lacks a clearance still reads the classified columns through a broader grant. **Effective Access** and **Verify** report such conflicts. A rule on an attribute evaluated per request, or on a non-user attribute, is refused, because a permanent grant cannot follow it.

Every change is a new revision with its author, recorded by the server. **Explain** shows the business rule, the resolved attributes of each matched and excluded user, the generated controls with their state on the server, the target nodes, and the result of the last deployment.

### Policy deployments {#data-access-deployments}

**Policy Deployments** computes the difference between the desired state of every enabled rule and the server, and shows it before anything changes:

- Only entities the platform owns, recorded in `dap_owned`, are changed or removed. An entity that exists but was not created by the platform is left alone and listed, with **Adopt** for generated names; a role a rule grants that a user already has from elsewhere is reported and kept when the rule stops applying.
- An owned entity that was removed outside the platform is reported and not restored, unless **Restore entities that were removed outside the platform** is chosen. To revoke an entitlement on purpose, add an exception to the rule.
- Statements are idempotent (`IF NOT EXISTS`, `OR REPLACE`, `IF EXISTS`), so deploying again repairs a partial deployment. With **Apply changes to: ON CLUSTER**, the result shows each server, and a server that did not answer is shown as unfinished.
- The page also lists rules that cannot be deployed, users who read a filtered table outside every rule, and disabled identities.

**Verify** checks that every generated control is present, and that no user known to the identity sources keeps a revoked access through another grant, and lists queries still running for those users. A revocation is reported complete only when these checks pass on the server the console is connected to; other servers of a cluster are covered by the per-server results of the deployment.

Deployments, reconciliations, and verifications are recorded in `dap_deployments` with the actor, the rules and revisions, each step with its per-server result, and the verification.

### Access policy worker {#access-policy-worker}

`utils/web-console/access_policy_worker.mjs` keeps the server in line with the rules when nobody has the console open. Each cycle it imports the attribute feed (when configured), computes the desired state with the same functions as the console, which it loads from `console.html`, applies the difference, and records ownership, the deployment, and an audit record.

```bash
CLICKHOUSE_URL=http://127.0.0.1:8123 CLICKHOUSE_USER=access_policy_worker CLICKHOUSE_PASSWORD=... \
    ATTRIBUTE_FEED=/var/lib/clickhouse-console/hr-feed.json ATTRIBUTE_FEED_SOURCE=hr INTERVAL_SECONDS=60 \
    node utils/web-console/access_policy_worker.mjs
```

The worker is not an escalation path: it holds no privilege to grant anything. Each statement runs as `EXECUTE AS <author>`, the user who wrote the current revision of the rule, so the server checks that user's own privileges, including the grant option and `CLUSTER` for `ON CLUSTER`. Its account needs:

```sql
GRANT SELECT ON console_admin.* TO access_policy_worker;
GRANT INSERT ON console_admin.dap_owned TO access_policy_worker;
GRANT INSERT ON console_admin.dap_deployments TO access_policy_worker;
GRANT INSERT ON console_admin.audit_log TO access_policy_worker;
GRANT INSERT ON console_admin.dap_user_attributes TO access_policy_worker;  -- only with a feed
GRANT SELECT ON system.users TO access_policy_worker;  -- and system.roles, system.role_grants, system.grants, system.row_policies
GRANT SHOW USERS, SHOW ROLES, SHOW ROW POLICIES ON *.* TO access_policy_worker;
GRANT IMPERSONATE ON <each rule author> TO access_policy_worker;
```

The feed is a JSON file or an `https://` URL (with `ATTRIBUTE_FEED_TOKEN` as a bearer token) of `[{"user": "...", "attributes": {"department": "...", ...}}]`. Only attributes defined with the feed's source are imported; a value the feed no longer reports is removed. Define the attributes with the worker's account as their writer.

**Revocation latency.** An attribute change reaches the server within one interval after the feed reports it (60 seconds by default), plus the delay of the feed itself. Grants and row policies are checked when a query starts: a running query finishes with the access it started with, and new queries of open sessions use the new access.

**Identity source outage.** When the feed cannot be read, nothing is written and the values age. Until they pass the freshness limit of their attribute, the access already provisioned stays active. After that, each rule applies its setting: **revoke** removes the access (row filters show no row), **keep** holds what was provisioned. Set the freshness limit to the longest outage you accept.

**Disabled identities.** A ClickHouse user authenticates with its own credentials, not with the identity provider. Disabling the identity (`employment_status`) removes what rules gave and makes row filter rules show no row, but the user can still sign in and use grants made outside the platform until the account is suspended on the **Users** page or dropped.

### Dynamic access and masking {#data-access-dynamic}

Request-time ABAC and column masking need an enforcement boundary that sees every query. Findings on this server version:

- **Native masking** is refused in this build (`SUPPORT_IS_DISABLED`: "Masking Policies are available only in ClickHouse Cloud"). The statement is parsed, so its syntax is no evidence of support. While checking it, `CREATE MASKING POLICY ... TO NONE` raised a logical error (inconsistent AST formatting of `TO NONE`): an exception in a release build.
- **Controlled views** with `SQL SECURITY DEFINER` read the base table as the definer while `currentUser()` returns the reader, so a view can decide per user, for example `if(currentUser() IN (SELECT user_name FROM <entitled users>), ssn, concat('***-', right(ssn, 2)))`. Checked on synthetic data: the entitled reader gets the value and the others the mask; a filter on the real value through the view matches nothing, because filters, joins, grouping, and ordering operate on the masked value; but whatever the mask leaves visible can be probed (`LIKE '***-1%'` matched), and the base table's row policies do not apply inside the view (the reader saw 2 rows instead of 1), so they must be repeated in the view. Such a view is safe only when the readers have no grant on the base table, and no other path (another view, a Distributed or Merge table, a dictionary, a materialized view, `remote()` with other credentials) reaches it. Hashing is not anonymization: a hash of a low-entropy value, such as a national identifier, is reversed by enumerating the values.
- **A query gateway** enforces only if no client can reach the server directly; ClickHouse has no mechanism that confines users to a gateway except network rules and the users' allowed hosts. Rewriting SQL needs the server's parser, not regular expressions.
- **An engine enhancement** (planner-level masking and request attributes) is the only option that covers every protocol and distributed execution; it is upstream work.

Recommendation: keep authorization in native controls (column grants, row policies, and the attribute-driven provisioning above). For masking, use controlled definer views only for named tables whose base-table access is revoked for all readers, and verify the absence of other paths with **Row Policies → Bypass paths** and access tests. The console does not provide request-time ABAC or masking, and nothing on this page is presented as such.

### Performance {#data-access-performance}

A row policy adds its filter to every query of the users it applies to, as if they had written it: on 50 million rows, `sum(v)` took 0.15 s with a policy `branch = 'north'` against 0.17 s with the same `WHERE` written by hand (median of 5 runs, on the development server). A policy disables the answer of `count()` from the table's metadata: `count()` took 0.10 s with the policy against 0.01 s without. Index the columns used in filters (the primary key or a skip index) on large tables.

### Data access tables {#data-access-tables}

**Set up** on the **Access Tests**, **Attributes & Classifications**, **Policy Rules**, or **Policy Deployments** tab creates them in the admin database. Column permissions, row policies, and effective access need no table.

| Table | Contents |
|---|---|
| `dap_attributes` | Attribute definitions, with source, writer, owner, and freshness. |
| `dap_user_attributes` | Attribute values, with their source, observation time, and writer. |
| `dap_classifications` | Column labels, with source and owner. |
| `dap_rules` | Rule revisions (`MergeTree`, one row per revision). |
| `dap_owned` | Entities created by the platform, by stable key. |
| `dap_deployments` | Deployments, reconciliations, and verifications, with per-step and per-server results. |
| `dap_access_tests` | Approved access tests. |
| `dap_test_runs` | Outcomes of test runs, kept for 365 days. |

As for the other console tables, the writer and time of each row are filled in by the server. Grant `SELECT` on them to the readers of the page, `INSERT` on the tables of each task (attributes, values, classifications, rules, tests, runs, and `dap_owned` for deployments) to its administrators, and keep `ALTER` and `DROP` to the server administrators.

Administrative changes are recorded in the console audit log (actions `dap_*`; search for `dap_` on **Audit Activity**). Query-time decisions are kept apart: **Audit Activity → Access decisions** shows reads the server refused (`ACCESS_DENIED` in `system.query_log`, with the literals of queries replaced by `?`) and the runs of access tests.

### Data access runbooks {#data-access-runbooks}

- **A user reads columns it should not.** Open **Effective Access** for the user and table: the "Given by" column names the grant and role path. Revoke the broader grant; a column grant does not narrow it.
- **A user sees every row.** **Row Policies → Effect on a table** shows "no policy applies": add the user (or a role it has at login) to a policy.
- **A deployment is partly applied.** The history shows the failed step and the servers. Fix the cause (often the author's missing grant option or `CLUSTER` privilege), then deploy again: the statements are idempotent.
- **An entity is reported as existing but not owned.** Remove or rename it, or **Adopt** it to let the platform manage it.
- **Revocation is not complete.** **Verify** lists the other grants that still give the access, and running queries. Revoke the other grants, or suspend the user.
- **The worker reports a failure.** The audit record names the step and the server's message; the worker acts as the rule author, so the author needs the privileges for every generated statement.
- **To migrate or recover**, back up the admin database with the other console tables. The native entities (roles, grants, row policies) are backed up with the access entities of the server (`BACKUP ... system.users`, roles, and row policies). After a restore, run **Verify**: drift between `dap_owned` and the server is reported, not silently repaired.

## Backup & Restore {#backup-and-restore}

The **Backup & Restore** page of the **Administration** category runs the native `BACKUP` and `RESTORE` statements of ClickHouse. It does not copy data itself. It adds what the statements lack: a list of approved destinations, a durable record of every operation, schedules, retention that keeps incremental chains intact, restores that do not touch existing data unless you ask, and restore tests.

| View | What it shows |
|---|---|
| Overview | Operations of the last 7 days (total, failed or unknown, running), available backups and how many passed a restore test, recent failures, schedules, destinations, and the last heartbeat of the backup worker. |
| Backups | The inventory: one row per backup with its scope, destination, type and base, size and file count when the server reported them, and checks (artifact opened, restore test). |
| Restore | The restore wizard for a chosen backup. |
| Schedules | Schedules with their next runs, and a retention preview. |
| Destinations | The approved destinations, their test results, and the allowed S3 endpoints. |
| Operations | Every backup, restore, restore test, deletion, and destination test, with its state and the source of that state. |
| Recovery verification | The restore tests and their checks. |

The page needs the console tables: when they are missing, the page offers **Set up**, which creates the [backup tables](#backup-tables) in the `admin_database`.

### Recovery coverage {#recovery-coverage}

A backup contains what `BACKUP` copies: nothing more. Plan the recovery of the rest separately.

| Object | Covered |
|---|---|
| Tables of the `MergeTree` family, `Log` family, and `Memory`: schema and data | Yes |
| Views, materialized views, dictionaries: definitions | Yes. The target table of a materialized view is backed up only if it is in the scope. |
| Tables of external engines (`S3`, `URL`, `Kafka`, `MySQL`, `PostgreSQL`, and similar): definitions | Yes; their data is stored elsewhere and is not backed up. The review step lists them. |
| Users, roles, settings profiles, quotas, row policies created with SQL | Only when chosen as a separate scope item |
| Users and settings in configuration files (`users.xml`), server configuration | No: keep them in configuration management |
| Named collections, including the S3 credentials of destinations | No |
| Keeper data other than the metadata of replicated tables | No |
| Point-in-time recovery | No. A backup is a snapshot of when each table was copied; changes between backups are lost. |

Each table is backed up from the data parts it has when its own backup starts. A backup of several tables is therefore not a transactionally consistent snapshot: rows inserted during the backup may be in one table and missing from another. The review step of the wizard says so, and lists unfinished mutations and running schema changes.

### Backup destinations {#backup-destinations}

Backups go only to destinations that an administrator added. Users choose a destination by name; they never type a path or a URL.

- **Disk**: a disk of the server that is allowed in `backups.allowed_disk`, and a prefix inside it. The prefix may not contain `..` or start with `/`.
- **S3**: an endpoint, a bucket, and a prefix. The endpoint is the S3-compatible server, in the same environment or an external one, typed as `https://host[:port]`. It must be an [allowed endpoint](#s3-endpoint-allowlist). The access key is stored by the server in a named collection `console_backup_<id>`, created with `CREATE NAMED COLLECTION` from the destination form. The console tables keep only the collection's name. The server masks the key in `system.query_log` and its logs, and the console never reads it back. HTTPS endpoints are verified with the server's usual certificate checks.

:::note
The server checks `remote_url_allow_hosts` only for redirects of `BACKUP TO S3`, not for the endpoint itself. A user with `WRITE ON S3` can therefore make the server send requests to any address it can reach, including internal and cloud metadata addresses. The console allows only the endpoints that `backup_s3_endpoints` allows. Do not grant `READ ON S3` or `WRITE ON S3` to users who should not have that ability outside the console.
:::

#### Allowed S3 endpoints {#s3-endpoint-allowlist}

S3 destinations can use only allowed endpoints. The server does not restrict the endpoint of `BACKUP TO S3` itself (see the note above), so this list keeps the console from sending backups, and their credentials, to an unintended server. The endpoints come from two places, both listed under **Allowed endpoints** on the **Destinations** tab:

- **The console.** **Allow endpoint** adds an exact endpoint, such as `http://13.140.150.86:9000`, or a domain pattern, such as `https://*.example.com`. When you add a destination at an endpoint that is not allowed yet, the review of the destination includes the step that allows it, with a warning. **Remove** takes an endpoint off the list; destinations that already use it keep working. This needs `SELECT` and `INSERT` on the `backup_endpoints` table, and every change is in the audit log. Installations set up before this table existed show **Set up** in the section.
- **The server configuration.** `backup_s3_endpoints` in the `web_console` section. These entries are shown in the console but changed only in the configuration. Patterns for any host (`https://*`, `*`) and link-local or metadata addresses can be allowed only here.

Each entry is one of:

| Entry | Allows |
|---|---|
| `https://minio.example.com:9000` | Exactly this endpoint. |
| `https://*.example.com` | Any subdomain of `example.com`, on the default port. Add `:port` to allow another port. |
| `https://*` or `http://*:9000` | Any host with this scheme (and port). |
| `*` | Any HTTP or HTTPS endpoint. |

Patterns never match internal addresses: `localhost`, loopback and private network addresses, link-local addresses including the cloud metadata service `169.254.169.254`, and names ending in `.internal` or `.local`. To use such an endpoint, allow it exactly. Link-local and metadata addresses (`169.254.0.0/16`, `fe80::/10`, `metadata.google.internal`, `instance-data`) can be allowed only in the server configuration. The console checks the address as typed. It cannot detect a public name that resolves to an internal address, so use patterns only for domains you trust. The configuration entries are read from `/console/config.json`, so a configuration reload applies a change.

For example, to allow a MinIO server on the internal network and the buckets of AWS S3 in the configuration:

```xml
<clickhouse>
    <web_console>
        <backup_s3_endpoints>http://10.0.4.20:9000, https://*.amazonaws.com</backup_s3_endpoints>
    </web_console>
</clickhouse>
```

The server, not the browser, connects to the endpoint: it must be reachable from the server, and from every server of a cluster that runs backups. The [backup worker](#backup-worker) reaches it too, to list and delete backups.

A new destination is disabled until it passes **Test**: the server writes a small backup of the destinations table to `<prefix>/_console_test/<uuid>` and opens it. Listing and deleting at the destination are tested by the [backup worker](#backup-worker) with its own credentials, which also removes the test backup. The test runs on the server the console is connected to. In a cluster, every server that runs backups needs the same access.

Removing a destination deletes neither its backups nor its named collection. When the credentials are no longer needed, drop the collection with `DROP NAMED COLLECTION`.

### Backup operations {#backup-operations}

The backup wizard asks for the scope (whole databases, tables, partitions of a table, and, as a separate item, access entities), a destination, and the type: full, or incremental on an earlier backup of the same scope and destination, whose artifact must open. The review step lists the objects, the external tables, the views that read from databases outside the scope, and the consistency statement above. The console can also capture the row count and a fingerprint (`groupBitXor(cityHash64(*))`) of each table before and after the backup, to compare restores with. When the source changed during the backup, the result says so and the values are not used for checks.

Each operation has an ID that is also the `id` setting of the native operation in `system.backups`, the `log_comment` of its statements, and the correlation ID of its audit records. Before submitting, the console records the operation (`queued`), then submits `BACKUP ... ASYNC` and records the outcome of the submission:

| State | Meaning |
|---|---|
| `queued` | Recorded, not yet accepted by the server. |
| `running` | Accepted by the server. |
| `succeeded`, `failed`, `cancelled` | Reported by the server (`system.backups`, then `system.backup_log`). |
| `unknown` | The console could not determine the outcome: the answer to the submission was lost, or the server has no record and the artifact could not be checked. Check the target before running the operation again. |

Operations run in the server. Closing the browser does not cancel them, and does not lose them: the next visit to the page, and every cycle of the backup worker, reconciles the unfinished operations. When the server no longer lists an operation, for example after a restart, the console opens the artifact: a complete backup is recorded as `succeeded`, a missing one as `failed` with the explanation that it was interrupted. An operation is never submitted twice: the server refuses a second backup with the same ID or location.

**Cancel** in the Operations view runs `KILL QUERY` for the server operation. The server removes the partial backup. Rows restored before a restore was cancelled stay in its target.

The server shows no progress of a running backup in percent, and the console does not estimate one: it shows the elapsed time, and the files and bytes written when the server reports them. When an S3 destination becomes unreachable, the server retries each request for about an hour (`backup_restore_s3_retry_attempts`), and the operation stays `running` until you cancel it. The destination test and the artifact checks use two attempts and fail in seconds.

### Restoring {#restoring}

The restore wizard checks the chain of the backup (every base must open), the target, the names, conflicts, and asks you to type the name of the first target database to confirm.

- **Target**: by default, a new database `restore_<database>_<time>` for each database of the backup, so a restore never touches existing data. `RESTORE DATABASE ... AS` rewrites the references of views and materialized views to the new database.
- **Conflicts**: the console uses `create_table = 'create'` and `create_database = 'create'` and never `allow_non_empty_tables`, so the server refuses to restore over an existing object instead of appending to it. When a target exists, the wizard stops and offers a separate **Drop** dialog, with what depends on the database, a typed confirmation, and its own audit record.
- **Access entities**: restored only when chosen, with `restore_access_entities`, as a separate step that needs the access management privileges.
- **Privileges and capacity**: the wizard checks the privileges with `CHECK GRANT` before starting, and shows the size of the backup and the free space of the default disk, or says that it is unknown and why.

After a restore, the console compares the target with the backup: the tables and their engines, the row counts, and, when the backup captured them, the fingerprints. Each check is recorded with the operation.

### Schedules and retention {#schedules-and-retention}

A schedule backs up chosen databases hourly, daily, or weekly at a time in a time zone, as full backups or as incremental backups with a full backup every N runs. Schedules are run by the [backup worker](#backup-worker), not by the browser or the server.

Daylight saving time changes are handled as follows. A run is due at the first minute, on or after the scheduled local time, of each local day (or hour). When the clock is set back and a local time occurs twice, the schedule runs at the first occurrence. When the clock is set forward and the local time does not exist, it runs at the first minute after the gap. A run that was missed because no worker was running is made once, when a worker starts within the same period; older missed runs are not made up.

Each run has an operation ID and an artifact name derived from the schedule and the local time of the run, so two workers that see the same run submit it only once. A run is postponed while another operation of the same schedule, destination, or databases is running. When the base of an incremental run is missing or does not open, the schedule either fails the run or makes a full backup, as chosen.

Retention keeps the last N chains (a full backup and the incremental backups based on it). The Schedules view previews which backups retention would delete. A backup that is the base of another backup that is kept is never deleted, by retention or by hand: the inventory marks it **Protected**, the deletion dialog refuses it, and the worker checks it again before deleting. Do not configure bucket lifecycle rules that expire objects of a backup prefix: they can delete a base and break the chains that depend on it.

Deletions are requested in the console and executed by the worker, because SQL cannot delete a backup.

### Recovery verification {#recovery-verification}

**Test restore** restores a backup into new databases named `console_verify_<id>_<database>` on the server the console is connected to, compares them with the backup and with the values captured when it was made, and drops them. The result is recorded with its checks, shown in the inventory and in **Recovery verification**, and audited; a failed test stays visible until a later one passes. Schedules can run a restore test after each backup.

A restore test shows that the backup opens and that its data matches, on this server. It does not test a restore on another server, of another version, or the recovery of what the backup does not cover.

### Backup worker {#backup-worker}

`utils/web-console/backup_worker.mjs` is a process that runs next to the server. It needs Node.js 18 or later and no packages. Each cycle (every 30 seconds by default) it:

- reconciles unfinished operations;
- submits due scheduled backups, and restore tests of schedules that ask for them;
- applies retention and executes requested deletions;
- tests listing and deleting at destinations, and removes destination test artifacts;
- records a heartbeat, shown on the Overview, and calls a webhook when a scheduled operation fails.

```bash
CLICKHOUSE_URL=http://127.0.0.1:8123 CLICKHOUSE_USER=backup_worker CLICKHOUSE_PASSWORD=... \
PROD_S3_ACCESS_KEY_ID=... PROD_S3_SECRET_ACCESS_KEY=... \
node utils/web-console/backup_worker.mjs
```

Run it as a service (for example with systemd) on the server host: deleting from a disk destination needs access to the disk's directory. Several workers may run at the same time. The worker reads S3 credentials from environment variables named after the destination's credential reference (`<REF>_ACCESS_KEY_ID`, `<REF>_SECRET_ACCESS_KEY`, `<REF>_REGION`), and a schedule's webhook URL from the variable named in the schedule. It writes only to the console tables, and logs JSON lines without credentials.

Its service account needs the privileges of a **Backup Administrator** (see below) for the databases of the schedules, the `SELECT` privilege on them for fingerprints, and `INSERT` on the four backup tables and the audit log.

### Backup privileges {#backup-privileges}

As everywhere in the console, every action is a statement run as you and authorized by the server. These are the privileges each action needs, and the role templates that bundle them:

| Action | Privileges |
|---|---|
| See the page | `SELECT` on the four backup tables |
| Back up | `BACKUP` on the scope; `READ, WRITE ON DISK`, or `NAMED COLLECTION` on the destination's collection and `READ, WRITE ON S3`; `INSERT` on `backup_operations`, `backup_events`, and `audit_log` |
| Restore | `READ ON DISK` or `READ ON S3` and the collection; `CREATE DATABASE`, `CREATE TABLE`, `CREATE VIEW`, `CREATE DICTIONARY`, `INSERT` on the target; for access entities, the access management privileges |
| Test restore | As restore, on `console_verify_*`, and `DROP DATABASE` on it |
| Check an artifact | `CREATE DATABASE, DROP DATABASE ON console_inspect_*.*` (the artifact is opened with the `Backup` database engine) |
| Manage destinations | `INSERT` on `backup_destinations`; for S3, `CREATE NAMED COLLECTION`, `ALTER NAMED COLLECTION`, `DROP NAMED COLLECTION` on `console_backup_*` |
| Allow S3 endpoints | `SELECT` and `INSERT` on `backup_endpoints` |
| Manage schedules | `INSERT` on `backup_schedules` |
| Cancel | `KILL QUERY` |

| Template | Grants |
|---|---|
| Backup Viewer | `SELECT` on the backup tables, the audit log, `system.backups`, `system.backup_log`, and `system.disks`; `SHOW DATABASES`. |
| Backup Operator | The viewer's, plus backing up the chosen databases to disks (optionally S3), checking artifacts, and requesting deletions; optionally `KILL QUERY`. |
| Restore Operator | The viewer's, plus restoring into new databases named `restore_*` and restore tests. It cannot drop databases other than its restore tests, or restore access entities. |
| Backup Administrator | All of the above for the chosen databases, plus destinations, allowed S3 endpoints, schedules, and `KILL QUERY`. |

`READ ON S3` and `WRITE ON S3` apply to every S3 URL, not only to the configured destinations, and `READ ON DISK` and `WRITE ON DISK` to every disk: grant them only to users trusted with that.

### Backup tables {#backup-tables}

| Table | Contents |
|---|---|
| `backup_destinations` | `ReplacingMergeTree`: one row per destination, without credentials. |
| `backup_schedules` | `ReplacingMergeTree`: one row per schedule. |
| `backup_operations` | `MergeTree`: one row per operation, written once when it is requested. |
| `backup_events` | `MergeTree`: the state changes and checks of each operation, appended. The current state is the latest event. |
| `backup_endpoints` | `ReplacingMergeTree`: the S3 endpoints allowed in the console, in addition to `backup_s3_endpoints`. |

### Backup runbooks {#backup-runbooks}

- **An operation is `unknown`.** Look at **Operations** for the source of the state and the error. For a backup, select **Check artifact** in the inventory: if the backup opens, it is usable. For a restore, inspect the target databases before restoring again into new ones.
- **A backup was interrupted.** A backup interrupted by a server failure is recorded as `failed`, and its partial files stay at the destination: select **Delete** on its row to have the worker remove them.
- **An operation stays `running`.** `system.backups` shows the server's view. For S3, check that the endpoint is reachable from the server, then cancel the operation. For `ON CLUSTER` operations, a server that does not answer makes the operation wait (see [Limitations](#limitations)).
- **A scheduled backup did not run.** On the Overview, check the worker heartbeat, then the worker's log. A run is skipped while an operation on the same databases or destination is running, and postponed runs are not made up after the period.
- **A deletion failed.** The operation shows the reason, for example that the backup is the base of another one, or that the worker has no credentials or no access to the disk directory. Partial deletions on S3 list the keys that remain.
- **A restore test failed.** The checks list the tables whose counts or fingerprints differ. A fingerprint difference with equal counts usually means the source changed during the backup without the console capturing it; test the next backup before relying on this one.
- **Recovering the console tables.** They are ordinary tables and can be in a backup's scope. Restore them into a new database and set `admin_database` to it, or copy their rows back.

## Cluster Management {#cluster-management}

The **Clusters** page of the **Administration** category manages the lifecycle of ClickHouse deployments: planning, provisioning, registration, configuration, scaling, maintenance, upgrades, recovery, decommissioning, and retirement.

ClickHouse has no SQL statement that creates servers, provisions infrastructure, or redistributes data, so the console does not pretend to. It records plans, versioned desired configurations, and operations in the console tables. The **cluster agent** (`utils/web-console/cluster_agent.mjs`), a process on the infrastructure host, executes them through a provider, checks every result, and records what it observes. The console never connects to the managed clusters and never handles their credentials: what it shows comes from the agent's observations, with the time they were made.

|---|---|

Filters: a search on name, identifier, owner, and workload; environment, provider, mode, and lifecycle; and **Needs attention** (drift, failed or blocked operations, or a cluster that is not healthy). |
| Create Cluster | The creation wizard. |
| Register Existing | Read-only registration of an existing deployment. |
| Overview | Identity, endpoints, secret references, health, recovery targets and measured evidence, recent operations. |
| Nodes & Topology | Shards, replicas, and their observed state, version, replication, background work, disk, and memory; restart and decommission. For registered deployments: the discovered topology with its provenance and conflicts. |
| Keeper | Members, roles, quorum, versions, and latency. |
| Configuration | Desired settings, observed differences, drift, and the revision history. |
| Capacity & Scaling | Capacity per node; resize, add a replica, add or remove a shard. |

### Kubernetes provider {#cluster-kubernetes}

The **kubernetes** provider deploys clusters with the [ClickHouse operator](https://github.com/ClickHouse/clickhouse-operator) of ClickHouse Inc. A cluster of the console is one `KeeperCluster` and one `ClickHouseCluster` (`clickhouse.com/v1alpha1`) named `chc-<id>`, in a namespace of the agent's Kubernetes cluster, with a Secret `chc-<id>-console` and, when chosen, a client Service `chc-<id>-client`. The operator creates the StatefulSets, pods, Services, ConfigMaps, and a volume claim per pod. The agent uses `kubectl` with fixed argument lists, and reaches the pods with `kubectl port-forward`: nothing is exposed for it outside the cluster.

It was verified with operator v0.0.8 (2026-09-25), cert-manager v1.16.2, and k3s v1.31.5 in k3d. The agent refuses an operator version it was not verified with (`CLUSTER_AGENT_OPERATOR_VERSIONS`). Behavior of that operator that the provider relies on:

- `replicas` is the number of replicas of every shard: all shards have the same size, and the operator adds or removes the replica or the shard with the highest index. The console therefore adds or removes one replica in every shard, and removes only the last shard.
- The cluster in `remote_servers` is named `default`, with an interserver secret; the macros `shard` and `replica` are indexes from 0; the `default` database is `Replicated`.
- Deleting the resources deletes the pods and Services, but not the volume claims: the StatefulSets retain them when deleted or scaled down.
- A larger data volume in the resource is applied by the operator to every claim; it fails on a storage class that does not allow expansion.
- Settings, resources, and the image are rolled out one replica at a time; the operator reports the result with conditions (`Ready`, `Healthy`, `ConfigurationInSync`, `ClusterSizeAligned`, `VersionInSync`), which the agent waits for before its own checks in ClickHouse.

#### Choices in the wizard {#cluster-kubernetes-choices}

| Volume sizes | Data volume per node, Keeper volume per member, in GiB | The claims of the operator. |
| Client Service | None, ClusterIP, NodePort, LoadBalancer | A Service in front of all ClickHouse pods, ports 8123 and 9000. |

chproxy is not offered on Kubernetes: use the client Service.

### Modes and states {#cluster-modes}

A cluster in the inventory is a platform-managed deployment. It is not the same as a named cluster in `remote_servers`: a deployment can define several, and an entry in `system.clusters` does not prove infrastructure ownership.

| Mode | Meaning |
|---|---|
| Observe | Inventory and monitoring only. Registered deployments start here. |
| Manage | Configuration and lifecycle operations through the provider. Clusters created in the console start here. |
| Retired | A historical record: observation and operations stop; the remaining resources are listed with their disposition. |

The lifecycle state (`planned`, `provisioning`, `validating`, `ready`, `degraded`, `unreachable`, `maintenance`, `failed`, `retiring`, `retired`) is separate from the state of each operation. A node is **unreachable** when it does not answer the agent; it is **failed** only when the provider confirms it, for example a container that is not running. An unreachable node is never taken as permission to delete its data or its replica metadata.

### Creating a cluster {#creating-a-cluster}

The wizard has eight steps:

1. **Purpose and ownership**: name, environment, owner, workload, expected data and growth, concurrency, ingestion, availability goal, and RPO and RTO targets. Sizing from these numbers is an estimate.
2. **Infrastructure provider**: only implemented providers can be chosen, and only when an agent offers them for the environment. With **kubernetes**, the step offers the namespace, storage class, volume reclaim policy, and client Service (see [Choices in the wizard](#cluster-kubernetes-choices)), and the later steps the volume sizes and the Keeper image; the cluster name is `default`, and chproxy is not offered.
3. **Topology**: shards, replicas per shard, Keeper members (1, 3, or 5), the cluster name, and the [client routing](#cluster-client-routing): none, or chproxy. The wizard explains what failures the topology tolerates, separately for replicas, the Keeper quorum, and the routing, and that a lab on one host is one failure domain.
4. **Storage and resources**: CPU and memory per node, the image, and the storage model (a local volume per node and per Keeper member).
5. **Security**: the administrator user of the cluster and its password (at least 12 characters, without spaces, quotes, `$`, `#`, or backslashes, typed twice). The browser encrypts the password with the public key that the cluster agent publishes (RSA-OAEP with SHA-256): the plan and the console tables contain only the ciphertext, which only that agent can decrypt. The agent writes the password to the secrets file of the deployment on its host, and the nodes read it from the environment; it appears in no plan, URL, log, or console table. The agent and chproxy use a separate user, `console_service`, with a password the agent generates, as it does the cluster secret and the interserver credentials. The cluster is ready only after the administrator user signs in on every node.
6. **Operational policies**: backup destination, maintenance window, and an optional notification reference.
7. **Plan**: the containers, volumes, network, endpoints, configuration, expected disruption, preconditions, readiness checks, and what happens if provisioning fails.
8. **Readiness**, done by the agent after submission: every node answers and authenticates, Keeper has a leader and a quorum, every node lists the topology, and a test database is written, replicated, read through the cluster, and dropped. The cluster is **ready** only after these checks, not when its containers run.

Provisioning is one durable operation. Submitting the same plan twice provisions once: the second operation is rejected. Every created resource is recorded with its owner operation. When provisioning fails, the resources created so far are listed under **Retirement**; submitting again reuses them, and **Delete resources** removes them.

### Registering an existing deployment {#registering-a-cluster}

**Register Existing** records a name, the HTTP endpoints of the nodes, and a credential reference: the agent reads `<REF>_USER` and `<REF>_PASSWORD` from its environment, so the browser never sees the credentials. Use a read-only account.

The agent connects to each endpoint and records the version, host name, macros, disks, Keeper sessions, users, and replicated tables of each node, and the named clusters each node reports. It records conflicting observations, such as different versions or different members for the same shard, and the provenance and confidence of every part. It changes, recreates, and rotates nothing. Endpoints that do not answer are recorded as unreachable.

A registered deployment stays in **Observe** mode. **Adopt** is offered only for providers that implement management; no provider integration exists for external deployments, so their adoption is rejected with that reason.

### Operations {#cluster-operations}

Every change is an operation with an identifier, the requester (filled in by the server), the revision of the desired configuration, its parameters, and events for every step with its evidence. The agent:

- runs operations one at a time per cluster, in the order they were requested;
- checks the requester's capability on the server before starting (`EXECUTE AS`), the environment, the mode, and whether the provider implements the operation; a refusal is recorded as **rejected**;
- records each step when it starts and when it is done; a restarted agent continues after the last completed step, and steps are written to be safe to repeat;
- tries a failing step at most 3 times, then marks the operation **needs an operator**: **Retry** runs it again, **Cancel** stops it;
- marks an operation **outcome unknown** when the provider does not answer in time, and checks again;
- when several agents run, lets the earliest claim of an operation win; an operation without progress for 10 minutes is taken over.

**Cancel** stops a running operation at its next step, until it passes its irreversible boundary (for example, stopping a node during decommissioning). Steps already done are not undone: infrastructure and database changes are not rolled back atomically. Each operation describes its recovery when it fails.

### Monitoring {#cluster-monitoring}

Every 30 seconds, the agent queries each node once (version, uptime, replication queue and delay, read-only replicas, merges, mutations, distributed queues, disk, memory, load, running and failed queries, Keeper sessions) and asks each Keeper member for `mntr`. Every value carries the time it was collected; the console marks observations older than two minutes as stale. The health of a cluster is derived from all its members, never from one node. Values the agent could not collect are shown as such.

### Configuration and drift {#cluster-configuration}

The desired configuration is versioned: every change is a new revision, with secrets referenced and never stored. **Change settings** edits a catalog of server settings (`max_concurrent_queries`, `max_connections`, `keep_alive_timeout`, `max_table_size_to_drop`, `background_pool_size`, `max_server_memory_usage_to_ram_ratio`) and settings of the default profile (`max_memory_usage`, `max_execution_time`, `max_threads`). The agent writes them to managed files on each node, reloads the configuration, and restarts the nodes, one at a time, only for settings that the server reports it cannot change without a restart (`changeable_without_restart`). It then checks the values on every node.

For managed clusters, the agent compares the desired values with what the nodes report, and the managed files with what it wrote. Differences are shown as **drift**, with two explicit choices: **Apply the desired configuration** writes the files again, and **Adopt the observed values** makes them the desired ones. Nothing is overwritten silently. Settings outside the catalog are not managed.

### Scaling {#cluster-scaling}

- **Resize** changes CPU and memory per node and recreates the nodes one at a time, after their peers have caught up. Storage cannot be resized by this provider.
- **Add replica** creates a node, copies the schema of a peer, waits until every replicated table has caught up and its row count matches, then updates the topology. The new replica is ready only after that.
- **Decommission** (on Nodes & Topology) removes a replica. It is refused for the last replica of a shard, for a Keeper member, and when the remaining replicas are not caught up or the Keeper quorum is uncertain.
- **Add shard** creates the nodes of a new shard with the schema of shard 1, empty. Existing rows stay where they are; Distributed tables route new rows by their sharding key over all shards from then on, which changes the shard of a key. The dialog requires an acknowledgement of this.
- **Remove shard** is accepted only for a shard without rows. Moving data between shards (source and target mappings, a sharding expression, backfill and catch-up, duplicate and missing-row checks, cutover) is not automated.

### Client routing with chproxy {#cluster-client-routing}

A cluster can be created with [chproxy](https://github.com/ContentSquare/chproxy), an HTTP proxy for ClickHouse, in front of its nodes. Choose **Client routing: chproxy** on the topology step, with:

- the image (`contentsquareplatform/chproxy:<version>`, already on the Docker host; the agent does not pull images);
- the proxy user that clients authenticate with, mapped to the administrative user of the nodes;
- the limits of that user: concurrent queries and the maximum time of a query.

The agent creates a `chproxy` container with an endpoint on `127.0.0.1` and a generated configuration. The configuration takes both passwords from the environment, so the file contains no secret. The password of the proxy user is `CH_PROXY_PASSWORD` in the secrets file of the deployment on the agent host; give it to applications through your secret management. chproxy checks every node every 5 seconds and sends queries only to healthy nodes.

The cluster is ready only after chproxy finds every node healthy, sends queries to them, and refuses a wrong password. The agent keeps chproxy in step with the cluster, reloading its configuration without restarting it:

- it adds new replicas and shards to the routing once they are ready;
- before stopping a node (decommissioning, restart, resize, upgrade), it takes the node out of the routing, and puts it back when the node has caught up;
- it removes decommissioned nodes and removed shards.

**Nodes & Topology** shows the endpoint, the proxy user and its limits, and the routed nodes with their health; the cluster is degraded when chproxy does not answer. chproxy routes HTTP only: clients of the native protocol connect to the nodes directly. chproxy itself is one container: when it stops, its clients lose access while direct connections keep working.

### Keeper {#cluster-keeper}

Keeper is a separate ensemble, created at provisioning with 1, 3, or 5 members. The Keeper view shows each member's role, version, znode count, and latency, and whether a quorum exists. Changing the ClickHouse replicas never resizes Keeper, and membership changes are not implemented. Operations that remove nodes stop when the quorum is uncertain.

Keeper keeps its log and snapshots in its own volumes. Table backups contain the data and metadata to recreate replicated tables, not the coordination state; after the loss of Keeper data, replicated tables are recovered with `SYSTEM RESTORE REPLICA`.

### Maintenance and upgrades {#cluster-upgrades}

**Restart** restarts nodes one at a time. Before each node, the other replicas of its shard must be caught up; after it, the node must answer and catch up. ClickHouse has no drain command. With chproxy, the agent takes the node out of its routing before stopping it and puts it back once the node has caught up, so clients of chproxy are not sent to it; queries already running on the node fail. Without chproxy, clients connected to the node reconnect. Inserts queued for distribution are sent after the restart.

**Upgrade** changes the image of the nodes:

1. the agent refuses a downgrade and a jump of more than a year of releases, and an image that is not on the host;
2. it requires a verified backup of the cluster from the last 24 hours, or a recorded reason to waive it;
3. it upgrades the other replicas of each shard before the first one, one node at a time;
4. after each node it checks that the node answers, reports the target version, catches up, and shows no load or data errors;
5. a failed check stops the rollout, and the remaining nodes keep the previous version;
6. after the last node, it checks the topology and replication.

Changing the image back does not downgrade data that the new version may have written. The recovery path is a restore of the pre-upgrade backup into a new cluster of the old version. Validate a target version in a lab cluster first.

### Protection and recovery {#cluster-recovery}

**Back up now** backs up every shard from a caught-up replica, without `ON CLUSTER`, to an S3 destination of Backup & Restore, then opens each shard's backup with the `Backup` database engine and reads back the row count of every table. Only a backup with that verification counts for upgrades and retirement. The Overview shows the recovery targets next to the measured evidence: the time of the last verified backup.

| Situation | Procedure |
|---|---|
| A replica failed, others are healthy | Decommission the failed node, then add a replica: it fetches the data from the healthy replicas. |
| Data lost on all replicas | Restore a verified backup into a new cluster, check it, then switch clients (not automated). |
| Infrastructure replaced | Create a cluster with the same topology, then restore its backup (restore not automated). |
| Keeper data lost | Recreate the ensemble, then run `SYSTEM RESTORE REPLICA` on each replicated table (not automated). |
| Switch to a recovery site | Fence the old deployment first, switch client routing, measure data freshness, plan failback (not automated; no cross-site provider). |

The console never creates a second authoritative deployment on its own: switching clients to a recovered cluster is an operator's decision.

### Decommissioning and retirement {#cluster-retirement}

Decommissioning a node: identify its roles; check the remaining replicas and the Keeper quorum; compare row counts when the node answers; check running queries and queued distributed inserts; take it out of the routing of chproxy, if the cluster has one; stop it (the irreversible boundary); remove it from the cluster definition; remove its replica metadata from Keeper with `SYSTEM DROP REPLICA` (justified because the agent stopped and removed the node); check the remaining cluster; remove the container; keep or delete its volume as chosen.

Retirement is separate from deletion:

1. **Dependency review**: applications and connections, ingestion pipelines, scheduled jobs, users and integrations, dashboards, backup schedules, and other dependencies each need a recorded disposition. Unknown is not accepted.
2. **Protection**: a verified final backup, or a recorded reason why none is needed (refused when the cluster holds data); the retention deadline of the retained resources; legal or operational holds.
3. **Execution**: the agent checks the dependencies, that no other operation is in progress, and the protection gate; then stops the containers, records every resource with its disposition and deadline, and sets the mode to Retired.
4. **Deletion**, a separate operation that needs the capability `destroy`: only the resources selected (**Select all** selects every remaining resource), only when Docker labels them as the cluster's, and not before their retention deadline. The result lists every resource as retained, stopped, or deleted, with its owner and evidence.

Backups made through Backup & Restore, the configuration history, the operations, and the audit records remain after retirement and deletion. A registered deployment is only retired from the inventory.

### Capabilities and audit {#cluster-capabilities}

Each capability is a column of the `cluster_capabilities` table, granted as `INSERT(<column>)`: `view_clusters`, `register`, `create_cluster`, `adopt`, `configure`, `scale`, `keeper`, `maintain`, `upgrade`, `recover`, `decommission`, `retire`, and `destroy`. The console checks them with `CHECK GRANT` to offer actions; the agent checks them again with `EXECUTE AS <requester> CHECK GRANT` before it executes an operation. Requesting an operation also needs `INSERT` on `cluster_operations`, `cluster_events`, and `cluster_revisions`.

| Template | Grants |
|---|---|
| Cluster Viewer | `SELECT` on the cluster tables and `backup_destinations`; `view_clusters`. |
| Cluster Operator | The viewer's, plus requesting operations, and `register`, `configure`, `maintain`, `scale`, `decommission`. |
| Cluster Administrator | Every capability, optionally including `destroy`, and `INSERT` on `clusters`. |

Plans, submissions, cancellations, and retries are audited by the console with the operation ID as correlation ID; the agent audits each result, failure, and rejection.

### Cluster tables {#cluster-tables}

| Table | Contents |
|---|---|
| `clusters` | `ReplacingMergeTree`: identity, environment, owner, provider, connection (endpoints and credential reference), requirements, and policies. |
| `cluster_revisions` | `MergeTree`: versioned desired configurations, and discovered descriptions of registered deployments. |
| `cluster_operations` | `MergeTree`: one row per operation, written once. |
| `cluster_events` | `MergeTree`: operation states and steps with evidence, claims, lifecycle, mode, drift, and agent heartbeats (kept 30 days). |
| `cluster_observations` | `MergeTree`: health observations, kept 7 days. |
| `cluster_resources` | `ReplacingMergeTree`: provider resources with their disposition, owner operation, retention deadline, and evidence. |
| `cluster_capabilities` | `Null` engine: holds no data; its columns are the capabilities. |

### Cluster runbooks {#cluster-runbooks}

- **Operations stay queued.** The inventory shows the agent's last heartbeat. Start the agent, and check that it serves the cluster's environment.
- **An operation is rejected.** The message names the missing capability, the environment, the mode, or the unsafe condition.
- **An operation needs an operator.** The failing step shows its message and evidence. Fix the cause (for example, pull a missing image), then **Retry**, or **Cancel**.
- **Provisioning failed.** The resources created so far are listed under Retirement. Submit the creation again from the plan, or delete the resources.
- **A cluster is degraded.** Nodes & Topology shows which nodes do not answer, and whether the provider confirms them failed. Keeper shows the quorum.
- **Drift.** Configuration lists the differences; apply the desired configuration or adopt the observed values.
- **An upgrade stopped.** The operation lists the upgraded nodes. Find the cause before continuing; to return, restore the pre-upgrade backup into a new cluster.

## Integration contract {#integration-contract}

The pages served by the server (`/dashboard`, `/binary`, `/merges`, `/schema`, `/jemalloc`, `/processors-profile`, and `/docs`) call `window.parent.clickhouseConsole.getConnection(window)` once at startup. When the page is embedded by the console on the same origin, this returns the server URL, the user, and the password, and the page hides its own connection fields. The console returns the connection only to frames it created for these pages, and only while you are signed in. When the page is opened on its own, or embedded by a page of another origin, the call is not made and the page behaves as before.

The Web Terminal receives the credentials in its existing `webterminal-credentials` message. The console sends it only to the terminal frame, with its own origin as the target origin.

The SQL Console has no embedding interface. The console fills in its connection form and submits it, as a user would. If that does not succeed, the console shows a notice above the panel, and you can sign in with the form of the SQL Console.

ClickStack is a separate application with its own connection settings, entered in ClickStack on first use. The console does not sign in to it. ClickStack shows a banner saying that this embedded version is not recommended for production use. The console closes that banner, the same way as its close button does (in the browser's local storage, which ClickStack opened on its own shares), and shows the message in a popup instead the first time ClickStack is opened after each sign-in, unless **Do not show this again** was selected.

## Limitations {#limitations}

- The console and the panels share the origin of the ClickHouse HTTP port. Any page on that origin, including ClickStack and the SQL Console, can read the memory of the console. Do not serve untrusted content from the ClickHouse HTTP port.
- Navigation inside an embedded page, for example opening a query in the SQL Console, also adds entries to the browser history.
- Panels other than the SQL Console, Dashboard, ClickStack, Web Terminal, and Reference are reloaded each time they are opened, which stops their background refresh while they are hidden.
- A theme change applies to panels opened after it. Panels that are already open keep their theme until they are reloaded.
- The Merges visualizer does not display query errors, including permission errors.
- The component access policy is enforced by the console only, and its tables are local to one server (see [Component access](#component-access)).
- The console cannot close another user's open native connections when suspending the user (see [Suspending a user](#suspending-a-user)).
- Quotas do not count queries that read no table, such as `SELECT 1`.
- Backups do not provide point-in-time recovery, and a backup of several tables is not a consistent snapshot of them (see [Recovery coverage](#recovery-coverage)).
- `BACKUP ... ON CLUSTER` waits for every server of the cluster. When one does not answer, the operation does not finish until `backup_restore_failure_after_host_disconnected_for_seconds` (an hour by default), and a server waiting for it does not shut down until then. The console runs backups on the server it is connected to.
- The server does not check `remote_url_allow_hosts` for the endpoint of `BACKUP TO S3`; the console restricts endpoints with `backup_s3_endpoints` (see [Backup destinations](#backup-destinations)).
- Restore tests run on the server the console is connected to, which shares resources with the production workload.
- Schedules, retention, and deletions need the [backup worker](#backup-worker). Without it, the page shows that no worker is running, and requested deletions stay `queued`.
- Cluster Management implements one provider, a Docker Compose lab on one host: its nodes are one failure domain, without TLS, storage resizing, or Keeper membership changes, and its optional chproxy is a single container (see [Supported capabilities](#cluster-capability-matrix)).
- Lifecycle operations need the [cluster agent](#cluster-setup). Without it, operations stay queued and observations become stale.
- Restoring a backup into a replacement cluster, moving data between shards, and switching traffic to a recovery site are not automated.
