The web console is a single entry point for the web UIs built into the ClickHouse server. It is served from any ClickHouse HTTP port at the `/console` path, for example `http://localhost:8123/console`.

Open the console, sign in with a ClickHouse user, and pick a panel on the home page. Panels open in the main area next to a sidebar that stays visible, so you can switch between the SQL Console, dashboards, and diagnostics without signing in to each of them.

## Panels {#panels}

The home page and the sidebar list the same destinations:

| Category | Destination | Path | How it receives the connection |
|---|---|---|---|
| Home | Home | `/console/home` | — |
| Workspace | SQL Console | `/ui` | The console fills in the connection form of the SQL Console. |
| Workspace | Dashboard | `/dashboard` | Console integration contract. |
| Workspace | ClickStack | `/clickstack` or `clickstack_url` | ClickStack keeps its own connection settings. |
| Workspace | Web Terminal | `/webterminal` | The `webterminal-credentials` message. |
| Diagnostics | Binary visualizer | `/binary` | Console integration contract. |
| Diagnostics | Merges visualizer | `/merges` | Console integration contract. |
| Diagnostics | Schema visualizer | `/schema` | Console integration contract. |
| Diagnostics | Jemalloc | `/jemalloc` | Console integration contract. |
| Diagnostics | Processors profile | `/processors-profile` | Console integration contract. |
| Administration | Users, Roles & Permissions, Component Access, Profiles & Quotas, Audit Activity | `/console/admin-*` | Pages of the console itself (see [Administration](#administration)). |
| Resources | Source code, Documentation, Website, Cloud | `source_code_url`, `documentation_url`, `website_url`, `cloud_url` | None: opened in a new tab. |
| Resources | Reference | `/docs` | Console integration contract. |

When a panel opens, the console header and sidebar hide, so that the panel, with its own navigation, uses the whole window. To return to the console navigation, select **Console** (the arrow at the start of the panel bar); select the same button again to hide it. The console navigation stays visible for that panel until you select another one. Home, the [Administration](#administration) pages, and the messages shown instead of a panel (for example when it is restricted or not configured) always show the console navigation. In the Web Terminal, Escape moves the keyboard focus to the **Console** button.

Each panel has a refreshable address under `/console`, for example `/console/merges`. The browser's Back and Forward buttons move between panels. The pages keep working on their own at their original paths.

After sign-in, the console runs a `LIMIT 0` query for each diagnostic panel with the privileges that panel needs. A panel is:

- Not listed when the server denies that query: the user has no privileges for the panel, so the console shows neither its card nor its sidebar entry. Its address, for example `/console/merges`, explains the restriction and can still open the panel; the server rejects every query the user is not allowed to run.
- **Unavailable** when a system table the panel needs does not exist, for example when `system.part_log` is not configured.
- **Not configured** when an administrator has removed its address (see [Configuration](#configuration)).
- **Needs Internet** when the page loads a library from a public CDN: the Binary visualizer loads Leaflet, and Jemalloc loads uPlot. Every other panel and the console itself work without Internet access.

The Web Terminal is unavailable when it is disabled with the `enable_webterminal` server setting, and when the console is connected to a server other than the one that serves it.

## Signing in and out {#signing-in-and-out}

The sign-in form has the same fields and URL rules as the [SQL Console](/interfaces/sql-console): the server URL, the username, and the password. The console checks them by running `SELECT currentUser(), version(), hostName()`, which needs no privileges. If the check fails, it tells apart:

- an incorrect username or password;
- a user that may not connect from your address, or that lacks permissions;
- a server that cannot be reached;
- a TLS certificate that the browser does not trust (the browser does not report the difference from an unreachable server, so the message names both);
- a request that the browser blocked: mixed content, or a CORS policy that does not allow the console's origin.

If you open a panel's address without being signed in, the console asks you to sign in and then opens that panel.

**Sign out** and **Switch connection** close every panel, which ends their queries, timers, and terminal sessions. They also discard the password and the ClickHouse connection that ClickStack stored for the current browser tab. After signing out, the Back button does not restore the signed-in state.

The home page shows the connection status the server reported at the last check. The console checks the connection again every minute while the tab is visible, and when you select **Check connection**.

## Security model {#security-model}

The sign-in screen is a convenience of the user interface, not an access control: the console page and the embedded pages are public static files, like the other web UIs. Every query is authorized by the ClickHouse server, with the credentials of the signed-in user. Hiding or marking a panel in the console does not change what the user can do.

Credentials are handled as follows:

- The console keeps the password in the memory of the browser tab. It is never written to the address bar, the browser history, cookies, or browser storage. Reloading the page signs you out.
- The console sends the credentials in the `X-ClickHouse-User` and `X-ClickHouse-Key` headers.
- Embedded pages get the credentials from the console without going through a URL, a storage, or a message to another origin (see [Integration contract](#integration-contract)). Some of them send the credentials to the server as `user` and `password` URL parameters, as they do when opened on their own. The ClickHouse server masks the password in its logs, but a reverse proxy may record such URLs: do not log query strings on a proxy in front of ClickHouse.
- Links to external destinations open in a new tab with `noopener` and `noreferrer`, and carry no credentials, queries, or database names.
- The console page is served with `Cache-Control: no-store`, `X-Frame-Options: DENY`, and a `Content-Security-Policy` that allows only inline code, same-origin frames, and requests to ClickHouse servers. To override any of these headers, set it in the [`http_handlers`](/interfaces/http#predefined_http_interface) configuration of a `console` handler.
- The embedded pages are loaded in same-origin frames. Do not set `X-Frame-Options: DENY` or `frame-ancestors 'none'` on them, or they cannot be embedded.

The SQL Console keeps its saved queries, query history, and open tabs in the browser's local storage, per server URL and user, also when it is used inside the console. Signing out of the console does not delete them.

## Configuration {#configuration}

The destinations of the resource links and of ClickStack are set in the `web_console` section of the server configuration. A path on the server is opened inside the console; an absolute HTTP or HTTPS URL is opened in a new tab; an empty value marks the destination as not configured. Other values are rejected.

| Setting | Default |
|---|---|
| `source_code_url` | `https://github.com/ClickHouse/ClickHouse/` |
| `documentation_url` | `https://clickhouse.com/docs/` |
| `website_url` | `https://clickhouse.com/` |
| `cloud_url` | `https://clickhouse.cloud/` |
| `clickstack_url` | `/clickstack/` |
| `admin_database` | `console_admin`: the database of the [administration tables](#console-tables) |
| `backup_s3_endpoints` | Empty: the S3 endpoints that [backup destinations](#backup-destinations) may use, separated by commas, for example `https://s3.eu-west-1.amazonaws.com,https://minio.example.internal:9000`. With an empty value, only disk destinations can be added. |

For example, in a network without Internet access, point the documentation to an internal mirror and remove the other external links:

```xml
<clickhouse>
    <web_console>
        <documentation_url>https://docs.example.internal/clickhouse/</documentation_url>
        <source_code_url></source_code_url>
        <website_url></website_url>
        <cloud_url></cloud_url>
    </web_console>
</clickhouse>
```

The console reads these settings from `/console/config.json`, so a configuration reload applies them without restarting the server.

To serve the console with custom response headers, use the `console` handler type in `http_handlers`. The console works only at `/console`, so the rule must match every path under it, including `/console/config.json`:

```xml
<clickhouse>
    <http_handlers>
        <rule>
            <url>regex:^/console(/.*)?$</url>
            <methods>GET,HEAD</methods>
            <handler>
                <type>console</type>
            </handler>
        </rule>
        <defaults/>
    </http_handlers>
</clickhouse>
```

## Administration {#administration}

The **Administration** category manages ClickHouse users, roles, settings profiles, and quotas, and the access policy of the console. Its pages are listed for users who can read what they show; for everyone else they are hidden. Hiding is a convenience only.

| Page | What it does |
|---|---|
| Users | Searchable, paginated list of users with their authentication methods, management source, roles, allowed hosts, profiles, quotas, and state. Each user has tabs for its overview, roles, permissions, profiles and quotas, component access, and audit activity. |
| Roles & Permissions | Roles with their privileges, members, and granted roles; grants and revokes of privileges on everything, a database, a table, or columns; role templates. |
| Component Access | Which console components each role or user can open, compared with the native privileges that actually govern them; protected accounts. |
| Profiles & Quotas | Settings profiles with limits and constraints, and quotas with their intervals and limits. |
| Audit Activity | Changes made in the console, and access-management statements that the server logged, including those made outside of the console. |

### Identity and authorization model {#identity-and-authorization-model}

The console has no identity provider and no server-side session: you sign in as a ClickHouse user, and the password stays in the memory of the browser tab. Every administrative action is a statement such as `CREATE USER` or `GRANT`, built by the console from validated form fields (it never runs SQL typed by the user), and run with your credentials. ClickHouse authorizes each statement:

- granting a privilege needs that privilege `WITH GRANT OPTION`, so you cannot hand out more than you have;
- granting a role needs `ROLE ADMIN`, or that role granted to you `WITH ADMIN OPTION`;
- user management can be limited to names: `GRANT CREATE USER, ALTER USER, DROP USER ON app_* TO ...` allows managing only the users whose names start with `app_`.

The console asks the server what you can do (`CHECK GRANT`, and `LIMIT 0` reads of system tables) to decide which pages and buttons to offer. The server still checks every statement, so a direct request without the console is rejected in the same way.

A ClickHouse user is a database identity. Creating one does not create an account in ClickStack or in any other separately deployed service, and the console does not synchronize identities with them.

Users defined in configuration files (`users.xml`) and users provided by an LDAP server are shown with their source and are read-only in the console: SQL statements cannot change them, and the console does not move users between sources. ClickHouse does not store e-mail addresses, creation dates, or the time of the last login, so the console does not show them; the last successful login is shown from `system.session_log` when that log is enabled.

### Setting up {#setting-up}

The Users, Roles & Permissions, and Profiles & Quotas pages work without setup. The audit log, the component access policy, and the protected accounts need tables: on the **Component Access** page, select **Set up**. This creates the database named by the `admin_database` setting (by default `console_admin`) with the [console tables](#console-tables), and a policy rule that lets all users open every component, so nothing changes for users until you edit the policy. The setup needs `CREATE DATABASE` (if the database does not exist) and `CREATE TABLE` on it.

Users who cannot read the policy table do not see the components it governs. The setup therefore creates the role `<admin_database>_reader` (by default `console_admin_reader`) with `SELECT` on the policy table, and offers to assign it to the existing users and roles created with SQL. The role must be among a user's default roles to apply at sign-in. When you create a user in the console, this role is preselected if you can grant it. A role is used instead of a direct grant because assigning a role needs only the admin option on it, while granting `SELECT` on the table would need it `WITH GRANT OPTION`.

To set up without the console, run the statements shown in the review step of the **Set up** dialog with `clickhouse-client`.

### User lifecycle {#user-lifecycle}

- **Create**: a name, a password (typed twice, or generated in the browser and shown once after the user is created), an optional expiry, the allowed hosts, a default database, roles, and a settings profile.
- **Edit**: rename, allowed hosts, and default database.
- **Password**: set a new password or generate a temporary one, with an optional expiry. This replaces every authentication method of the user. ClickHouse cannot force a password change at the next login; use an expiry instead. Users authenticated by LDAP, Kerberos, certificates, SSH keys, JWT, or HTTP cannot get a password in the console.
- **Roles**: assign and revoke roles, set the default roles, and grant the admin option.
- **Delete**: shows what depends on the user (roles, privileges, views with `SQL SECURITY DEFINER` that run as the user, quotas, row policies, and running queries) and asks you to type the name.

Passwords are sent to the server only in the statement that sets them, never in a URL. The server stores a hash and masks the password in `system.query_log` and its logs. The console does not write passwords to the audit log, to error messages, or to browser storage, and removes a generated password from the page when its dialog closes.

### Suspending a user {#suspending-a-user}

ClickHouse has no statement that disables a user. The console suspends a user with `ALTER USER name VALID UNTIL '2000-01-01 00:00:00 UTC'`, which makes every authentication method of the user expire. Then:

- new logins are rejected over every interface. HTTP requests are authenticated one by one, including those with a `session_id`, so HTTP clients of the user stop working at their next request;
- native connections that are already open, such as `clickhouse-client`, the Web Terminal, and pooled driver connections, keep working until they disconnect. ClickHouse has no statement that closes another user's connection. To cut them off at once, revoke the user's roles and privileges as well: revocations apply to open sessions at their next query;
- running queries finish, unless you also select **Stop running queries**, which runs `KILL QUERY` and needs the `KILL QUERY` privilege;
- roles, privileges, and settings stay unchanged.

**Reactivate** sets `VALID UNTIL 'infinity'` or a date you choose. Expiry dates that the user had before the suspension are overwritten; they are kept in the audit record and shown when reactivating.

### Roles and templates {#roles-and-templates}

The permissions of a user or role are shown as direct privileges, privileges inherited from roles (with the role path, and whether the role is a default role, which is active at login, or needs `SET ROLE`), and the effective privileges computed by the server (`SHOW GRANTS ... FINAL`). Grants with the grant option and roles with the admin option are marked, because they allow delegation.

The role templates are proposals of the console, not built-in ClickHouse roles. None includes the grant option or unrestricted administrative rights. The console shows each template's exact privileges before creating a role, and the server refuses any privilege you do not hold `WITH GRANT OPTION`.

| Template | Privileges |
|---|---|
| Platform Administrator | `SELECT, INSERT` on the three console tables; `SHOW USERS, SHOW ROLES ON *.*`. |
| ClickHouse Access Administrator | `CREATE USER, ALTER USER, DROP USER ON <pattern>`; `SHOW USERS, SHOW ROLES, SHOW SETTINGS PROFILES, SHOW QUOTAS ON *.*`; `SELECT, INSERT` on the audit log and `SELECT` on the policy and the protected accounts; the chosen roles and, once the console is set up, `<admin_database>_reader` `WITH ADMIN OPTION`; optionally `KILL QUERY ON *.*`. |
| Database Administrator | On each chosen database: `SHOW, SELECT, INSERT, ALTER, CREATE TABLE, CREATE VIEW, CREATE DICTIONARY, DROP TABLE, DROP VIEW, DROP DICTIONARY, TRUNCATE, OPTIMIZE`, and `SYSTEM MERGES, SYSTEM TTL MERGES, SYSTEM MOVES, SYSTEM FETCHES, SYSTEM REPLICATION QUEUES, SYSTEM SYNC REPLICA, SYSTEM RESTART REPLICA`. |
| Developer | On each chosen database: `SHOW, SELECT, INSERT, ALTER TABLE, ALTER VIEW, CREATE TABLE, CREATE VIEW, DROP TABLE, DROP VIEW, TRUNCATE, OPTIMIZE`; `CREATE TEMPORARY TABLE ON *.*`. |
| Analyst | `SHOW TABLES, SHOW COLUMNS, SELECT` on each chosen database. |
| Operator | `SELECT` on `system.dashboards`, `metric_log`, `asynchronous_metric_log`, `metrics`, `events`, `asynchronous_metrics`, `part_log`, `merges`, `mutations`, `replicas`, `parts`, `disks`, `clusters`, `tables`, `columns`, `dictionaries`, `jemalloc_stats`, `documentation`; optionally `system.processes`, `query_log`, and `processors_profile_log` (they contain the queries of all users) and `INTROSPECTION`. |
| Auditor | `SHOW USERS, SHOW ROLES, SHOW SETTINGS PROFILES, SHOW QUOTAS, SHOW ROW POLICIES ON *.*`; `SELECT` on the three console tables, `system.query_log`, and `system.session_log`. |

The access administrator pattern `*` lets the role change any user, including administrators: prefer a prefix.

### Component access {#component-access}

The policy has rules for all users, for roles, and for users. Each rule allows four capabilities of a component: **Open**, **View data**, **Run queries**, and **Administer**. A capability is allowed when any rule for all users, for the signed-in user, or for one of the roles enabled in the session allows it; components without a rule that allows **Open** are not listed, and their address shows that the policy does not allow them. The policy governs the panels and the links of the **Resources** section (Source code, Documentation, Website, Cloud, and Reference); for a link, only **Open** applies. Home and the administration pages are not governed, so a policy mistake cannot lock administrators out. A component that no rule mentions yet, such as one added to the console after the policy was set up, is open to everyone; on the Component Access page it is marked **No rules yet**, and saving the rules for all users turns that into a rule. Hiding a link only removes it from the console: anyone who knows the address of an external site can still visit it.

The console enforces only **Open**. The SQL Console, the standalone pages, the Web Terminal, and other clients reach the server directly, where only native privileges apply. For the other capabilities, the Component Access page shows the native privileges that govern them (for example `SELECT ON system.part_log` for the Merges visualizer), whether a role or user has them, and offers to grant the missing ones or revoke direct grants where the policy and the grants disagree. ClickStack has its own connection settings and authorization, and the Web Terminal is enabled for everyone by the `enable_webterminal` server setting: the policy only hides them in the console.

When the policy table exists but the user cannot read it, the console does not list the governed components and says so on the home page.

### Protected accounts and platform administrators {#protected-accounts}

Protected accounts are users that the console does not delete or suspend, for example break-glass accounts. Users defined in configuration files cannot be changed with SQL at all, which makes them the most robust break-glass accounts.

Platform administrators are the users who can change the policy (`INSERT` on its table, directly, through roles, or through broader grants). The console estimates them from `system.grants` and refuses to delete or suspend the last one, to revoke the last role that makes someone one, or to delete such a role.

These safeguards are applied by the console only. A user with the privileges can still make the same changes with SQL directly.

### Clusters {#clusters}

Changes apply to the server the console is connected to. When the server has clusters and its SQL-managed users are not in a replicated user directory, the administration pages offer **Apply changes to: ON CLUSTER**. Each statement then runs with `ON CLUSTER` and `distributed_ddl_output_mode = 'never_throw'`, and the result shows every server with its outcome. A server that does not answer within 30 seconds is shown as unfinished: it executes the statement when it processes the distributed DDL queue. A change that fails on some servers is reported as partially applied; it is not rolled back. When users are stored in a `replicated` user directory, every change reaches all servers that share it through Keeper, and the console does not offer `ON CLUSTER`.

Statements of one change run one after another and stop at the first failure, because ClickHouse has no transactions for access entities. The result lists the steps that took effect.

The console tables are stored on the server the console is connected to, and are not replicated.

### Audit activity {#audit-activity}

The **Console actions** tab shows the records that the console writes after each change: the actor, the time, the server, the scope (this server or a cluster), the target, the action, a summary, the result (`success`, `failure`, or `partial`), a sanitized error, and the steps with the outcome on each server. Each change has a correlation ID, which the console also sets as the `log_comment` of its statements.

The **Access changes seen by the server** tab shows `CREATE`, `ALTER`, and `DROP` statements for users, roles, profiles, quotas, and policies, and `GRANT` and `REVOKE`, from `system.query_log`, including rejected attempts. Statements with a console correlation ID are marked as made in the console, all others as made outside of it. This covers only the server the console is connected to, and does not cover users or sessions with `log_queries` disabled, changes to configuration files, or statements older than the `query_log` retention.

The pages always read the current state from the server, so a change made outside of the console is shown on the next load or refresh.

### Console tables {#console-tables}

| Table | Contents |
|---|---|
| `audit_log` | `MergeTree` with the console's audit records. Records older than the retention chosen at setup (365 days by default) are removed by a TTL. |
| `component_policy` | `ReplacingMergeTree` with one row per subject and component, read with `FINAL`. |
| `protected_accounts` | `ReplacingMergeTree` with the protected users. |

The actor, the time, and the server of each row are columns that the server fills in (`MATERIALIZED currentUser()`, `now64()`, and `hostName()`), with `CHECK` constraints that reject other values even when `insert_allow_materialized_columns` is enabled. So a user who can insert into these tables cannot write rows in another user's name. They are ordinary tables, though: users with `ALTER`, `TRUNCATE`, or `DROP` on them can change or remove rows, so the audit log is not tamper-proof. Grant only `SELECT` and `INSERT` on them, and keep `ALTER` and `DROP` to the server administrators. To change the retention later, run `ALTER TABLE console_admin.audit_log MODIFY TTL toDateTime(event_time) + INTERVAL <days> DAY`.

To remove the administration data, drop the database. The console then works as if it was never set up.

## Backup & Restore {#backup-and-restore}

The **Backup & Restore** page of the **Administration** category runs the native `BACKUP` and `RESTORE` statements of ClickHouse. It does not copy data itself. It adds what the statements lack: a list of approved destinations, a durable record of every operation, schedules, retention that keeps incremental chains intact, restores that do not touch existing data unless you ask, and restore tests.

| View | What it shows |
|---|---|
| Overview | Operations of the last 7 days (total, failed or unknown, running), available backups and how many passed a restore test, recent failures, schedules, destinations, and the last heartbeat of the backup worker. |
| Backups | The inventory: one row per backup with its scope, destination, type and base, size and file count when the server reported them, and checks (artifact opened, restore test). |
| Restore | The restore wizard for a chosen backup. |
| Schedules | Schedules with their next runs, and a retention preview. |
| Destinations | The approved destinations, their test results, and the S3 endpoint allowlist. |
| Operations | Every backup, restore, restore test, deletion, and destination test, with its state and the source of that state. |
| Recovery verification | The restore tests and their checks. |

The page needs the console tables: when they are missing, the page offers **Set up**, which creates the [backup tables](#backup-tables) in the `admin_database`.

### Recovery coverage {#recovery-coverage}

A backup contains what `BACKUP` copies: nothing more. Plan the recovery of the rest separately.

| Object | Covered |
|---|---|
| Tables of the `MergeTree` family, `Log` family, and `Memory`: schema and data | Yes |
| Views, materialized views, dictionaries: definitions | Yes. The target table of a materialized view is backed up only if it is in the scope. |
| Tables of external engines (`S3`, `URL`, `Kafka`, `MySQL`, `PostgreSQL`, and similar): definitions | Yes; their data is stored elsewhere and is not backed up. The review step lists them. |
| Users, roles, settings profiles, quotas, row policies created with SQL | Only when chosen as a separate scope item |
| Users and settings in configuration files (`users.xml`), server configuration | No: keep them in configuration management |
| Named collections, including the S3 credentials of destinations | No |
| Keeper data other than the metadata of replicated tables | No |
| Point-in-time recovery | No. A backup is a snapshot of when each table was copied; changes between backups are lost. |

Each table is backed up from the data parts it has when its own backup starts. A backup of several tables is therefore not a transactionally consistent snapshot: rows inserted during the backup may be in one table and missing from another. The review step of the wizard says so, and lists unfinished mutations and running schema changes.

### Backup destinations {#backup-destinations}

Backups go only to destinations that an administrator added. Users choose a destination by name; they never type a path or a URL.

- **Disk**: a disk of the server that is allowed in `backups.allowed_disk`, and a prefix inside it. The prefix may not contain `..` or start with `/`.
- **S3**: an endpoint from `backup_s3_endpoints`, a bucket, and a prefix. The access key is stored by the server in a named collection `console_backup_<id>`, created with `CREATE NAMED COLLECTION` from the destination form. The console tables keep only the collection's name. The server masks the key in `system.query_log` and its logs, and the console never reads it back. HTTPS endpoints are verified with the server's usual certificate checks.

:::note
The server checks `remote_url_allow_hosts` only for redirects of `BACKUP TO S3`, not for the endpoint itself. A user with `WRITE ON S3` can therefore make the server send requests to any address it can reach, including internal and cloud metadata addresses. The console allows only the endpoints in `backup_s3_endpoints`. Do not grant `READ ON S3` or `WRITE ON S3` to users who should not have that ability outside the console.
:::

A new destination is disabled until it passes **Test**: the server writes a small backup of the destinations table to `<prefix>/_console_test/<uuid>` and opens it. Listing and deleting at the destination are tested by the [backup worker](#backup-worker) with its own credentials, which also removes the test backup. The test runs on the server the console is connected to. In a cluster, every server that runs backups needs the same access.

Removing a destination deletes neither its backups nor its named collection. When the credentials are no longer needed, drop the collection with `DROP NAMED COLLECTION`.

### Backup operations {#backup-operations}

The backup wizard asks for the scope (whole databases, tables, partitions of a table, and, as a separate item, access entities), a destination, and the type: full, or incremental on an earlier backup of the same scope and destination, whose artifact must open. The review step lists the objects, the external tables, the views that read from databases outside the scope, and the consistency statement above. The console can also capture the row count and a fingerprint (`groupBitXor(cityHash64(*))`) of each table before and after the backup, to compare restores with. When the source changed during the backup, the result says so and the values are not used for checks.

Each operation has an ID that is also the `id` setting of the native operation in `system.backups`, the `log_comment` of its statements, and the correlation ID of its audit records. Before submitting, the console records the operation (`queued`), then submits `BACKUP ... ASYNC` and records the outcome of the submission:

| State | Meaning |
|---|---|
| `queued` | Recorded, not yet accepted by the server. |
| `running` | Accepted by the server. |
| `succeeded`, `failed`, `cancelled` | Reported by the server (`system.backups`, then `system.backup_log`). |
| `unknown` | The console could not determine the outcome: the answer to the submission was lost, or the server has no record and the artifact could not be checked. Check the target before running the operation again. |

Operations run in the server. Closing the browser does not cancel them, and does not lose them: the next visit to the page, and every cycle of the backup worker, reconciles the unfinished operations. When the server no longer lists an operation, for example after a restart, the console opens the artifact: a complete backup is recorded as `succeeded`, a missing one as `failed` with the explanation that it was interrupted. An operation is never submitted twice: the server refuses a second backup with the same ID or location.

**Cancel** in the Operations view runs `KILL QUERY` for the server operation. The server removes the partial backup. Rows restored before a restore was cancelled stay in its target.

The server shows no progress of a running backup in percent, and the console does not estimate one: it shows the elapsed time, and the files and bytes written when the server reports them. When an S3 destination becomes unreachable, the server retries each request for about an hour (`backup_restore_s3_retry_attempts`), and the operation stays `running` until you cancel it. The destination test and the artifact checks use two attempts and fail in seconds.

### Restoring {#restoring}

The restore wizard checks the chain of the backup (every base must open), the target, the names, conflicts, and asks you to type the name of the first target database to confirm.

- **Target**: by default, a new database `restore_<database>_<time>` for each database of the backup, so a restore never touches existing data. `RESTORE DATABASE ... AS` rewrites the references of views and materialized views to the new database.
- **Conflicts**: the console uses `create_table = 'create'` and `create_database = 'create'` and never `allow_non_empty_tables`, so the server refuses to restore over an existing object instead of appending to it. When a target exists, the wizard stops and offers a separate **Drop** dialog, with what depends on the database, a typed confirmation, and its own audit record.
- **Access entities**: restored only when chosen, with `restore_access_entities`, as a separate step that needs the access management privileges.
- **Privileges and capacity**: the wizard checks the privileges with `CHECK GRANT` before starting, and shows the size of the backup and the free space of the default disk, or says that it is unknown and why.

After a restore, the console compares the target with the backup: the tables and their engines, the row counts, and, when the backup captured them, the fingerprints. Each check is recorded with the operation.

### Schedules and retention {#schedules-and-retention}

A schedule backs up chosen databases hourly, daily, or weekly at a time in a time zone, as full backups or as incremental backups with a full backup every N runs. Schedules are run by the [backup worker](#backup-worker), not by the browser or the server.

Daylight saving time changes are handled as follows. A run is due at the first minute, on or after the scheduled local time, of each local day (or hour). When the clock is set back and a local time occurs twice, the schedule runs at the first occurrence. When the clock is set forward and the local time does not exist, it runs at the first minute after the gap. A run that was missed because no worker was running is made once, when a worker starts within the same period; older missed runs are not made up.

Each run has an operation ID and an artifact name derived from the schedule and the local time of the run, so two workers that see the same run submit it only once. A run is postponed while another operation of the same schedule, destination, or databases is running. When the base of an incremental run is missing or does not open, the schedule either fails the run or makes a full backup, as chosen.

Retention keeps the last N chains (a full backup and the incremental backups based on it). The Schedules view previews which backups retention would delete. A backup that is the base of another backup that is kept is never deleted, by retention or by hand: the inventory marks it **Protected**, the deletion dialog refuses it, and the worker checks it again before deleting. Do not configure bucket lifecycle rules that expire objects of a backup prefix: they can delete a base and break the chains that depend on it.

Deletions are requested in the console and executed by the worker, because SQL cannot delete a backup.

### Recovery verification {#recovery-verification}

**Test restore** restores a backup into new databases named `console_verify_<id>_<database>` on the server the console is connected to, compares them with the backup and with the values captured when it was made, and drops them. The result is recorded with its checks, shown in the inventory and in **Recovery verification**, and audited; a failed test stays visible until a later one passes. Schedules can run a restore test after each backup.

A restore test shows that the backup opens and that its data matches, on this server. It does not test a restore on another server, of another version, or the recovery of what the backup does not cover.

### Backup worker {#backup-worker}

`utils/web-console/backup_worker.mjs` is a process that runs next to the server. It needs Node.js 18 or later and no packages. Each cycle (every 30 seconds by default) it:

- reconciles unfinished operations;
- submits due scheduled backups, and restore tests of schedules that ask for them;
- applies retention and executes requested deletions;
- tests listing and deleting at destinations, and removes destination test artifacts;
- records a heartbeat, shown on the Overview, and calls a webhook when a scheduled operation fails.

```bash
CLICKHOUSE_URL=http://127.0.0.1:8123 CLICKHOUSE_USER=backup_worker CLICKHOUSE_PASSWORD=... \
PROD_S3_ACCESS_KEY_ID=... PROD_S3_SECRET_ACCESS_KEY=... \
node utils/web-console/backup_worker.mjs
```

Run it as a service (for example with systemd) on the server host: deleting from a disk destination needs access to the disk's directory. Several workers may run at the same time. The worker reads S3 credentials from environment variables named after the destination's credential reference (`<REF>_ACCESS_KEY_ID`, `<REF>_SECRET_ACCESS_KEY`, `<REF>_REGION`), and a schedule's webhook URL from the variable named in the schedule. It writes only to the console tables, and logs JSON lines without credentials.

Its service account needs the privileges of a **Backup Administrator** (see below) for the databases of the schedules, the `SELECT` privilege on them for fingerprints, and `INSERT` on the four backup tables and the audit log.

### Backup privileges {#backup-privileges}

As everywhere in the console, every action is a statement run as you and authorized by the server. These are the privileges each action needs, and the role templates that bundle them:

| Action | Privileges |
|---|---|
| See the page | `SELECT` on the four backup tables |
| Back up | `BACKUP` on the scope; `READ, WRITE ON DISK`, or `NAMED COLLECTION` on the destination's collection and `READ, WRITE ON S3`; `INSERT` on `backup_operations`, `backup_events`, and `audit_log` |
| Restore | `READ ON DISK` or `READ ON S3` and the collection; `CREATE DATABASE`, `CREATE TABLE`, `CREATE VIEW`, `CREATE DICTIONARY`, `INSERT` on the target; for access entities, the access management privileges |
| Test restore | As restore, on `console_verify_*`, and `DROP DATABASE` on it |
| Check an artifact | `CREATE DATABASE, DROP DATABASE ON console_inspect_*.*` (the artifact is opened with the `Backup` database engine) |
| Manage destinations | `INSERT` on `backup_destinations`; for S3, `CREATE NAMED COLLECTION`, `ALTER NAMED COLLECTION`, `DROP NAMED COLLECTION` on `console_backup_*` |
| Manage schedules | `INSERT` on `backup_schedules` |
| Cancel | `KILL QUERY` |

| Template | Grants |
|---|---|
| Backup Viewer | `SELECT` on the backup tables, the audit log, `system.backups`, `system.backup_log`, and `system.disks`; `SHOW DATABASES`. |
| Backup Operator | The viewer's, plus backing up the chosen databases to disks (optionally S3), checking artifacts, and requesting deletions; optionally `KILL QUERY`. |
| Restore Operator | The viewer's, plus restoring into new databases named `restore_*` and restore tests. It cannot drop databases other than its restore tests, or restore access entities. |
| Backup Administrator | All of the above for the chosen databases, plus destinations, schedules, and `KILL QUERY`. |

`READ ON S3` and `WRITE ON S3` apply to every S3 URL, not only to the configured destinations, and `READ ON DISK` and `WRITE ON DISK` to every disk: grant them only to users trusted with that.

### Backup tables {#backup-tables}

| Table | Contents |
|---|---|
| `backup_destinations` | `ReplacingMergeTree`: one row per destination, without credentials. |
| `backup_schedules` | `ReplacingMergeTree`: one row per schedule. |
| `backup_operations` | `MergeTree`: one row per operation, written once when it is requested. |
| `backup_events` | `MergeTree`: the state changes and checks of each operation, appended. The current state is the latest event. |

As with the other console tables, the requester and the time are filled in by the server. Rows are never updated: deleting a backup appends a `deleted` event.

### Backup runbooks {#backup-runbooks}

- **An operation is `unknown`.** Look at **Operations** for the source of the state and the error. For a backup, select **Check artifact** in the inventory: if the backup opens, it is usable. For a restore, inspect the target databases before restoring again into new ones.
- **A backup was interrupted.** A backup interrupted by a server failure is recorded as `failed`, and its partial files stay at the destination: select **Delete** on its row to have the worker remove them.
- **An operation stays `running`.** `system.backups` shows the server's view. For S3, check that the endpoint is reachable from the server, then cancel the operation. For `ON CLUSTER` operations, a server that does not answer makes the operation wait (see [Limitations](#limitations)).
- **A scheduled backup did not run.** On the Overview, check the worker heartbeat, then the worker's log. A run is skipped while an operation on the same databases or destination is running, and postponed runs are not made up after the period.
- **A deletion failed.** The operation shows the reason, for example that the backup is the base of another one, or that the worker has no credentials or no access to the disk directory. Partial deletions on S3 list the keys that remain.
- **A restore test failed.** The checks list the tables whose counts or fingerprints differ. A fingerprint difference with equal counts usually means the source changed during the backup without the console capturing it; test the next backup before relying on this one.
- **Recovering the console tables.** They are ordinary tables and can be in a backup's scope. Restore them into a new database and set `admin_database` to it, or copy their rows back.

## Integration contract {#integration-contract}

The pages served by the server (`/dashboard`, `/binary`, `/merges`, `/schema`, `/jemalloc`, `/processors-profile`, and `/docs`) call `window.parent.clickhouseConsole.getConnection(window)` once at startup. When the page is embedded by the console on the same origin, this returns the server URL, the user, and the password, and the page hides its own connection fields. The console returns the connection only to frames it created for these pages, and only while you are signed in. When the page is opened on its own, or embedded by a page of another origin, the call is not made and the page behaves as before.

The Web Terminal receives the credentials in its existing `webterminal-credentials` message. The console sends it only to the terminal frame, with its own origin as the target origin.

The SQL Console has no embedding interface. The console fills in its connection form and submits it, as a user would. If that does not succeed, the console shows a notice above the panel, and you can sign in with the form of the SQL Console.

ClickStack is a separate application with its own connection settings, entered in ClickStack on first use. The console does not sign in to it. ClickStack shows a banner saying that this embedded version is not recommended for production use. The console closes that banner, the same way as its close button does (in the browser's local storage, which ClickStack opened on its own shares), and shows the message in a popup instead the first time ClickStack is opened after each sign-in, unless **Do not show this again** was selected.

## Limitations {#limitations}

- The console and the panels share the origin of the ClickHouse HTTP port. Any page on that origin, including ClickStack and the SQL Console, can read the memory of the console. Do not serve untrusted content from the ClickHouse HTTP port.
- Navigation inside an embedded page, for example opening a query in the SQL Console, also adds entries to the browser history.
- Panels other than the SQL Console, Dashboard, ClickStack, Web Terminal, and Reference are reloaded each time they are opened, which stops their background refresh while they are hidden.
- A theme change applies to panels opened after it. Panels that are already open keep their theme until they are reloaded.
- The Merges visualizer does not display query errors, including permission errors.
- The component access policy is enforced by the console only, and its tables are local to one server (see [Component access](#component-access)).
- The console cannot close another user's open native connections when suspending the user (see [Suspending a user](#suspending-a-user)).
- Quotas do not count queries that read no table, such as `SELECT 1`.
- Backups do not provide point-in-time recovery, and a backup of several tables is not a consistent snapshot of them (see [Recovery coverage](#recovery-coverage)).
- `BACKUP ... ON CLUSTER` waits for every server of the cluster. When one does not answer, the operation does not finish until `backup_restore_failure_after_host_disconnected_for_seconds` (an hour by default), and a server waiting for it does not shut down until then. The console runs backups on the server it is connected to.
- The server does not check `remote_url_allow_hosts` for the endpoint of `BACKUP TO S3`; the console restricts endpoints with `backup_s3_endpoints` (see [Backup destinations](#backup-destinations)).
- Restore tests run on the server the console is connected to, which shares resources with the production workload.
- Schedules, retention, and deletions need the [backup worker](#backup-worker). Without it, the page shows that no worker is running, and requested deletions stay `queued`.
